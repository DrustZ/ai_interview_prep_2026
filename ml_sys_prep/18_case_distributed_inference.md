## 0. 第一句话就要分叉：这是两道题 ⭐⭐⭐

面试官说"设计一个分布式推理系统"时，**不要立刻画架构图**。先问一句：

> 是**在线低延迟 serving**（用户在等），还是**离线批量推理**（跑数据集、生成训练数据、批量打标）？这两个的目标函数完全相反，架构选择也不一样——如果两个都要，我会当成两套系统来设计，共享模型权重和引擎，但调度层、SLO、容量规划全部分开。

### 目标函数对照表

| 维度 | 在线 serving | 离线批量推理 |
|---|---|---|
| **主指标** | 在 SLO 内的 **goodput**（达标请求数/秒） | **$/M token** 或 job wall-clock |
| **延迟** | p99 TTFT、p99 TPOT 是硬约束 | 不存在。只有 job 级 deadline |
| **batch size** | 受 SLO 上限约束，不能拉满 | 拉到显存 85% 上限 |
| **请求到达** | 外生、泊松式、有尖峰 | **全部已知**，可排序、分桶、重排 |
| **抢占** | 不可接受（除非引擎内部 KV 抢占） | **常态，是设计核心** |
| **失败处理** | 返回 5xx，用户重试 | 必须自动续跑 + 幂等 |
| **硬件** | 需要稳定预留容量 + 冗余 | spot / 抢占实例 / 碎片时段 |
| **长请求** | 污染别人的 p99（队头阻塞） | 只影响 job 尾巴，可隔离到单独桶 |
| **利用率目标** | 60–70%（留尖峰余量） | 越接近 100% 越好 |
| **扩缩容** | 冷启动几分钟 → 必须预热池 | 有多少要多少，随时让出 |

**高分句**：在线系统的成本结构里，**你为峰值买单，却按均值收益**；离线系统没有峰值这个概念，所以它的正确做法恰恰是在线系统的禁忌——把 batch 拉满、接受抢占、用最便宜的碎片算力。把两个场景混在一起谈，就会得出"既要低延迟又要高吞吐"这种没有信息量的答案。

### 一个物理事实决定了全部：prefill 与 decode 不是同一种负载

| 阶段 | 计算特性 | 瓶颈 | 一次处理多少 token |
|---|---|---|---|
| **Prefill** | 整个 prompt 并行过一遍，矩阵乘 | **compute-bound**（算力） | 整个 prompt（几千个） |
| **Decode** | 每步只生成 1 个 token，但要读全部权重 | **memory-bandwidth-bound**（显存带宽） | 每序列 1 个 |

具体到 70B 模型（fp16 权重 140 GB）在 8×H100（聚合带宽 8 × 3.35 = 26.8 TB/s）：

- **decode 一步的理论下限** = 140 GB ÷ 26.8 TB/s ≈ **5.2 ms**。跟 batch 多大**无关**——这就是为什么"不 batch 的 decode 是在烧钱"：单流 5.2 ms/token ≈ 190 tok/s，GPU 算力利用率不到 1%。
- **prefill 一次 2000 token** ≈ 2 × 70e9 × 2000 = 2.8e14 FLOP，8 张卡按 40% MFU 算 ≈ 3168 TFLOPS → **88 ms**。这就是 TTFT 的地板。

**这条物理事实推出了后面几乎所有的设计决策**：batching 之所以是免费的吞吐，是因为 decode 的权重读取被摊薄了；prefill/decode 分离之所以成立，是因为它们的瓶颈资源不同；投机解码之所以在小 batch 有效、大 batch 反而有害，是因为它用算力换带宽——而算力在大 batch 时已经不富余了。

## 1. 先问清楚：8 个澄清问题 ⭐⭐

每个问题后面写清楚"这个答案会改变什么设计决策"——面试里要**说出来**，不要只问不说。

| # | 问题 | 答案改变什么 |
|---|---|---|
| 1 | **在线还是离线？** 如果在线，SLO 是 TTFT 还是 TPOT 主导？ | 决定整篇的走向。TTFT 主导 → prefill 算力和 chunked prefill；TPOT 主导 → 并发上限和 KV 预算 |
| 2 | **模型多大、什么架构？**（参数量、层数、KV head 数、是否 MoE） | 决定权重是否单卡放得下 → 决定要不要 TP/PP。GQA vs MHA 决定 KV/token 差 8 倍，直接决定并发数 |
| 3 | **上下文长度分布**：p50 / p99 的 prompt 和 output 长度 | 长上下文让 KV 而不是权重成为显存和带宽瓶颈；长尾长请求决定要不要分桶隔离 |
| 4 | **QPS 的均值和峰谷比**（在线）／**总 token 量和 deadline**（离线） | 峰谷比决定要不要弹性伸缩；峰谷比 3× 且冷启动 3 分钟 → 只能靠预热池 + 准入控制 |
| 5 | **输出可不可以流式？** | 能流式的话 TTFT 是体感指标，输出速率只要跟得上人的阅读速度（约 15–20 tok/s，即 TPOT < 50–65 ms）就够；不能流式则端到端延迟 = TTFT + N × TPOT |
| 6 | **硬件是独占的还是共享/可抢占的？** | 这题最容易被忽略但最影响架构。共享池 → 整个 pause/resume 框架和自适应并发是必需品而不是优化 |
| 7 | **质量能不能降级？** 量化、小模型兜底、截断输出是否可接受？ | 决定成本下限。不能降级 → 只能加卡；能降级 → 量化和级联能省 2–4 倍 |
| 8 | **多租户吗？谁在竞争、优先级怎么定？** | 单租户只需要 FIFO；多租户要谈配额、公平性、抢占策略、优先级反转 |

**加分**：问完之后主动说"如果你更想聊某一侧，我可以深入"。这比自顾自讲 20 分钟好。

## 2. 指标先于方案：这个系统怎么算成功 ⭐⭐⭐

### 在线：为什么不能只报吞吐、不能只看均值

| 指标 | 定义 | 为什么必须有 |
|---|---|---|
| **TTFT** p50/p95/p99 | 请求到第一个 token | 用户感知的"卡不卡"。受**排队 + prefill** 共同影响 |
| **TPOT / ITL** p50/p99 | token 间隔 | 决定"流得顺不顺"。受 decode step time 和并发数影响 |
| **Goodput** | **满足 SLO 的**请求数/秒 | 唯一正确的容量指标。raw throughput 高但 90% 超时是负分 |
| **排队时间**（单独度量！） | 请求到达 → 进入 running batch | 见下 |
| **KV cache 利用率** | 已分配块 / 总块 | > 90% 就快要触发抢占/重算了，是最好的领先指标 |
| **抢占/重算率** | 引擎因 KV 不足踢出序列的比例 | 非零就说明并发调过头了 |

**必须单独度量排队时间**，理由很硬：

> p99 端到端 = 排队 + prefill + N × decode。如果只测端到端，你无法区分"该加卡"和"该修调度器"——这两个的解法完全不同，而且加错了钱白花。

**为什么均值是骗人的**：把系统近似成 M/M/1，利用率 ρ 下的排队等待 ≈ ρ/(1−ρ) × 服务时间。

| 利用率 ρ | 排队等待（服务时间的倍数） |
|---|---|
| 0.5 | 1× |
| 0.8 | 4× |
| 0.9 | **9×** |
| 0.95 | **19×** |

所以"GPU 利用率 90% 很健康"这句话在在线系统里是错的——**它意味着排队时间是服务时间的 9 倍**。均值可能还是 200 ms，p99 已经 5 秒了。在线系统的稳态利用率通常只能做到 60–70%，剩下的是买延迟。**这是在线和离线最本质的成本差异，不是工程水平差异。**

### 离线：换一套指标

| 指标 | 定义 | 说明 |
|---|---|---|
| **$/M output token** | 见 §5 公式 | 主指标 |
| **Goodput（离线版）** | **最终进入数据集**的样本数 / GPU-hour | 被过滤掉的 rollout 是浪费的算力。这才是真正的分母 |
| **tokens/GPU-hour** | 原始吞吐 | 工程指标，不是业务指标 |
| **有效并发 / 目标并发** | AIMD 收敛在哪 | 反映共享池的真实可用容量 |
| **抢占率 & 恢复时长** | 每小时被抢几次、恢复要多久 | 决定检查点粒度（§6） |
| **重试率 / dead-letter 数** | | 非零且增长 = 有 poison pill |
| **wall-clock ETA 及其误差** | | ETA 一直往后飘 = 并发在退化，要报警 |

**高分句**：离线批量真正的指标是 **goodput per GPU-hour——最终留在数据集里的样本数除以算力**，不是 tokens/s。因为一个跑得飞快但生成的东西 60% 会被质量过滤掉的 pipeline，成本比一个慢但产出干净的高。这也是为什么我愿意花 12% 的算力做前置筛选（§4.2）。

## 3. 在线低延迟 serving

> ⚠️ **诚实边界（重要）**
>
> 我**没有在线 serving 的 oncall 经验**。这一节我能讲清楚机制、能做容量估算、能推演故障模式，但我讲不出"某次线上事故我们怎么处置的"。面试里我会明说：
>
> > 在线这一侧我是从引擎实现和论文层面理解的，能做容量和成本推演；但我没有背过在线 pager。如果你想听真实的事故复盘，我能讲的是离线批量侧的——比如共享 GPU 池被抢占导致 job 反复重启、以及我们怎么用自适应并发把它稳住的。
>
> **不要编造 p99 战争故事。** 面试官问两层就穿帮，而且诚实标注边界本身在成熟团队里是加分项。

### 3.1 Continuous batching：为什么它是分水岭

静态 batching：把 N 个请求凑一批，一起 prefill，一起 decode，**等最长的那个结束才释放整批**。如果 batch 里有一个要生成 2000 token、其余只要 50，那 GPU 有 97% 的时间在为一个请求空转。

Continuous batching（也叫 iteration-level scheduling，Orca OSDI'22 提出，vLLM/TGI/SGLang 都实现了）：**每生成一步就重新调度一次**——完成的序列立刻离开，等待的序列立刻补进来。

| | 静态 batching | Continuous batching |
|---|---|---|
| 调度粒度 | 请求级 | **迭代级（每个 decode step）** |
| 尾部浪费 | 与输出长度方差成正比 | 接近零 |
| 新请求等待 | 等下一批 | 等下一步（毫秒级） |
| 公开报告的吞吐增益 | 基线 | 数倍到十几倍（依赖长度方差；方差越大增益越大） |

**面试要点**：continuous batching 的收益**完全来自输出长度的方差**。如果所有请求输出长度一样，它退化成静态 batching。所以先问长度分布——这也是澄清问题 3 的用处。

### 3.2 PagedAttention / KV cache 管理

KV cache 显存的精确公式（面试白板上要能直接写）：

```
KV bytes per token = 2 (K和V) × n_layers × n_kv_heads × head_dim × dtype_bytes
总 KV = 上式 × Σ(每个序列的当前长度)
```

代入常见模型：

| 模型 | layers | kv_heads | head_dim | **KV/token (fp16)** | 8k 上下文单序列 |
|---|---|---|---|---|---|
| Llama-3.1-8B (GQA) | 32 | 8 | 128 | **128 KiB** | 1.0 GB |
| Llama-3.1-70B (GQA) | 80 | 8 | 128 | **320 KiB** | 2.6 GB |
| 同规模但 MHA（64 heads） | 80 | 64 | 128 | **2.5 MiB** | 21 GB |

**GQA 是 8 倍的并发数差异**——这就是为什么所有现代大模型都用 GQA/MQA/MLA。面试里能报出这个倍数比会念"GQA 减少 KV" 强得多。

**PagedAttention 解决什么**：预分配连续显存要按 `max_seq_len` 预留，实际用不到 → 内部碎片；不同序列长度不一 → 外部碎片。vLLM 论文报告朴素方案浪费 60–80%，分页后 < 4%。做法照搬 OS 虚拟内存：KV 切成固定块（默认 16 token 一块），逻辑块 → 物理块查 block table，物理块不必连续。副产品是**共享**：同一 prompt 采样多条（正是 RL rollout 的场景）、beam search、共享系统前缀，都可以 copy-on-write 共享物理块。

**抢占是引擎内部就有的**：KV 池满了，vLLM 会踢掉一些序列（默认策略是重算 recompute，也可以 swap 到 CPU）。踢掉意味着那条序列的 prefill 白做了。**监控里必须有 preemption 计数**——它是"并发调过头"的直接证据，而不是要靠 p99 反推。

### 3.3 Prefill 与 decode 分离

两条路线，要能说清取舍：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **Chunked prefill**（同一池） | 把长 prefill 切块，与 decode 混在同一 batch 里跑 | 不需要额外集群；消除长 prompt 造成的 decode 卡顿（TPOT 尖刺） | prefill 被拉长，TTFT 略升；仍然是资源共享，互相干扰没有根除 |
| **PD disaggregation**（分池） | prefill 集群和 decode 集群物理分开，KV 通过互联传过去 | 两边可以用不同并行度、不同硬件、独立扩缩容；SLO 互不污染 | **KV 传输开销**：70B、2000 token prompt = 2000 × 320 KB ≈ **640 MB**；400 Gbps IB（≈50 GB/s）要 13 ms |

**判断规则**：TTFT 预算是几百毫秒量级时，13 ms 的 KV 传输可以接受，分离划算；如果 TTFT 预算只有几十毫秒，或者互联只有以太网（传 640 MB 要几百毫秒），分离就是负收益。**先算这个数再决定，不要背结论。**

### 3.4 投机解码：什么时候是负收益

机制：小 draft 模型（或 n-gram / EAGLE / Medusa 这类轻量头）先猜 k 个 token，大模型一次前向**并行验证**，按拒绝采样接受前缀。数学上输出分布与直接采样**完全等价**（分布意义上，不是逐样本相同）——这点要说，它是这个技巧能用的前提。

接受率 α、猜 k 步时，每次验证期望产出 token 数 = (1 − α^(k+1)) / (1 − α)。

**关键判断（大多数候选人答不出）**：

> 投机解码是**用算力换带宽**。小 batch 时 GPU 是 memory-bound，算力白白闲置，拿它换延迟是纯赚；**大 batch 时 GPU 已经接近 compute-bound，投机解码抢走的算力本来可以服务更多请求——此时它会降低总吞吐**。所以它是一个**在线小并发场景**的优化，在离线批量里几乎永远不该开。

### 3.5 并行策略取舍

| 策略 | 通信量 | 适用 | 陷阱 |
|---|---|---|---|
| **TP**（张量并行） | 每层 2 次 all-reduce，**每个 token 都要** | 单节点内（NVLink）；降单请求延迟 | 跨节点做 TP 会被网络吃掉；TP 度越大，通信占比越高，边际收益递减 |
| **PP**（流水线并行） | 只在 stage 边界传激活，量很小 | 跨节点、互联差；模型放不下时 | **decode 阶段流水线气泡严重**（每步只有 1 个 token 可流），对延迟不友好；适合吞吐场景 |
| **EP**（专家并行，MoE） | all-to-all | MoE 模型 | 负载不均：热门专家成为瓶颈 |
| **DP**（多副本） | 零 | 权重放得下时的**首选** | 每个副本一份权重，显存换吞吐 |

**决策顺序（可以直接背）**：
1. 权重 + 目标并发的 KV **单卡放得下** → 单卡 + 多副本 DP。最简单也最省。
2. 放不下 → 节点内 TP，TP 度取"刚好放得下 + 留够 KV 预算"的最小值。
3. 单节点还放不下 → 跨节点加 PP（吞吐场景）或 TP over 高速互联（延迟场景）。
4. 任何时候：**并行度不是越大越好**。TP=8 时通信可能占 20–30% 的 step time，而 TP=4 两副本的总吞吐通常更高。

### 3.6 自动扩缩容与冷启动：为什么它没那么容易

冷启动时间构成（70B 为例）：

| 阶段 | 耗时 |
|---|---|
| 拉权重：140 GB，从对象存储 1–2 GB/s | **70–140 s** |
| 从本地 NVMe（若已缓存） | 10–20 s |
| 加载到显存 + 并行切分 | 10–30 s |
| CUDA graph capture / torch.compile 预热 | 30–120 s |
| **合计** | **典型 2–5 分钟** |

**结论**：你无法用扩缩容应对一分钟级的流量尖峰。必须承认这个约束，然后：

- **预热池**：保留 N 个已加载好的空闲副本，成本换响应速度。这是最主要的手段。
- **按队列深度扩容**，不是按 GPU 利用率——利用率是滞后指标，队列深度是领先指标。
- **加滞回（hysteresis）**：扩容阈值和缩容阈值必须不同，否则在冷启动周期里会震荡（扩了还没起来，指标又降，开始缩，缩完又涨）。
- **准入控制 + 降级**是尖峰的真正答案：排队超过阈值直接拒绝（快速失败好过全体超时）、降到小模型、缩短 max_tokens。
- 权重放本地 NVMe 缓存 / 用 P2P 分发，能把最大的一块砍掉。

## 4. 离线批量推理：候选人的主场 ⭐⭐⭐

> ✅ **这一节我做过。** Reflection.ai mid-training 团队，为 RL 合成 math/STEM 数据：共享 GPU 池、被其他团队抢占是常态、自建 pause/resume 框架、TCP 式自适应并发调节、多阶段 LLM 流水线。下面的每条都能展开讲。

### 4.0 离线批量为什么是一道独立的系统题

不是"把在线系统的 batch 调大"。核心差别在于**信息结构**：离线场景里**所有请求在 t=0 就全部已知**。这解锁了在线系统做不到的四件事：

1. **可以重排**：按长度分桶、按共享前缀聚类，都是纯收益。
2. **可以丢弃和重排优先级**：先跑最可能有用的（见 4.2 的探测）。
3. **可以接受任意抢占**：没有用户在等，只要最终跑完。
4. **可以把利用率推到 95%+**：没有 p99 需要保护。

工业界已经把这个区分**明码标价**了：Anthropic Message Batches API 和 OpenAI Batch API 都是**标准价格的 50%**，代价是 SLA 从"秒级"变成"多数 1 小时内、最长 24 小时"。这是一个非常好的面试引用——它证明"延迟约束值多少钱"是有市场定价的，大约是 2 倍。

### 4.1 架构骨架

```
work list (所有样本 id + config hash，一次生成、只读)
   ↓
sharder：按 (prompt_len 桶, expected_output_len 桶, prefix 聚类) 分片
   ↓
work queue（持久化，支持 lease + 重新入队）
   ↓
worker pool（每个 worker = 1 组 GPU + 1 个推理引擎）
   ├─ AIMD 并发控制器（§4.3）
   ├─ SIGTERM handler → drain → checkpoint → 退出（§6）
   └─ append-only 结果分片写入（按 id 幂等）
   ↓
manifest / 索引：已完成的 id 集合 → 续跑时做差集
```

**关键设计原则：work list 一次生成、不可变、按内容哈希。** sample_id = hash(输入内容 + 模型版本 + 采样参数 + prompt 模板版本)。这样：
- 续跑 = 扫描已完成 id，和 work list 做差集，跑剩下的。
- 改了 prompt 模板 → hash 变了 → 自动重跑，不会拿旧结果冒充新结果。**这条能防住一整类"数据集里混了旧版本产出"的静默事故。**

### 4.2 推理预算的分配：自适应难度筛选 ⭐⭐⭐

这是我做过的、最能讲的一块，而且它把**推理系统**和**训练信号**连起来了。

**问题**：为 RL 生成 rollout，正式跑是每题 128 条。但很多题目**全对或全错**——在 GRPO 这类 group-relative 的算法里，组内 reward 全同 → advantage 全零 → **梯度贡献为零**。这些算力是纯浪费。

**做法**：正式 rollout 前先用 **16 条小批量探测可解率**，全对或全错的直接丢弃，保留的再跑 128 条。

**为什么 16 这个数不是拍脑袋——盈亏平衡点可以算**：

```
不筛选的成本            = 128
筛选后的成本（丢弃率 f）= 16 + (1−f) × 128
盈亏平衡： 16 + (1−f)·128 = 128  →  f = 12.5%
```

也就是说：**只要丢弃率超过 12.5%，筛选就是净赚**；而 16/128 = 12.5% 恰好就是"用于筛选的算力占比"。实际丢弃率在 40% 量级时，总算力 = 16 + 0.6×128 = 92.8，相对 128 **省 27%**，而且留下的样本每一条都带梯度信号——goodput 的提升远大于 27%。

**这个思想和 DAPO 的 dynamic sampling 一致**（面试可以主动点出来，显示不是闭门造车）。

**诚实的技术细节（会加分的两条）**：

1. **16 条的统计精度是有限的。** 16 条全对时，p 的单侧 95% 置信下界约 **0.83**（因为 0.83^16 ≈ 0.05）。所以我们其实在丢掉一部分真实可解率 ≈ 0.85 的题，它们的组内 advantage 标准差 √(0.85×0.15) ≈ 0.36，不是零。**这是一个用少量信号损失换算力的显式取舍，不是免费午餐**；阈值应该按下游 reward 曲线调，而不是死守"全对全错"。
2. **探测和正式跑的采样参数必须一致**（temperature、top_p、max_tokens、system prompt 全部）。任何一项不同，探测出的可解率就不是正式跑的无偏估计，整个筛选逻辑失效。这是很容易犯又很难发现的错。

### 4.3 自适应并发：TCP 式 AIMD ⭐⭐⭐

**为什么需要它**：共享 GPU 池里，可用容量是**其他团队的函数**，是一个移动靶。固定并发数只有两种结局——设低了长期欠打（利用率低），设高了持续 OOM / 429 / 被抢占（级联失败，还会拖垮别人）。

**做法**（照搬 TCP 拥塞控制）：

```
成功窗口（连续 N 个请求无失败信号） → concurrency += 1        (加性增)
观测到容量类失败                     → concurrency *= 0.5      (乘性减)
下界 concurrency >= 1；上界 = 引擎的 max_num_seqs
每个 worker 的探测周期加 jitter（避免全体同步造成羊群效应）
```

**最容易做错的一点（面试主动讲）**：

> **必须区分"容量类失败"和"输入类失败"。** 429、OOM、被抢占、连接超时 → 是容量信号，应该退避；单条样本 400（prompt 超长）、输出解析失败、内容策略拒绝 → 是**样本自身的问题**，退避它没有任何用，只会让并发在一个 poison pill 面前一路降到 1，整个 job 卡死。这两类错误必须分开计数、分开处理——**这是我们实际踩过的坑**。

**为什么是 AIMD 而不是 PID 或者别的**：AIMD 的收敛性和公平性是有理论保证的（多个竞争者会收敛到公平份额），而且它无状态、无需调参、对突变鲁棒。共享池里同时跑着多个 job，AIMD 让它们自动分摊而不是互相踩踏。

**配套的 Little's Law**：稳态下 `并发 L = 吞吐 λ × 单请求耗时 W`。所以并发是唯一的控制旋钮：想提吞吐只能提并发（W 由模型和长度决定）。这也是容量规划的公式——**在线场景反着用它**：目标 100 req/s、平均 10 s，就需要 1000 个请求同时在飞；1000 × 8k token × 0.32 MB/token = 2.6 TB 的 KV——一眼就能看出单机做不到，需要多少节点也随之算出来了。

### 4.4 长度分桶与前缀聚类

因为请求全部已知，可以做在线系统做不到的重排：

| 手段 | 收益 | 注意 |
|---|---|---|
| **按 output 长度预估分桶** | 同桶内长度接近 → KV 预留更准、抢占更少、尾部更整齐 | output 长度只能预估（可用 prompt 特征回归或历史统计），估错要有兜底 |
| **按 prompt 长度分桶** | 避免一个 100k token 的 prompt 和一堆 500 token 的挤在一起 | |
| **超长样本单独一个桶、单独一批 worker** | 隔离长尾，防止它们拖垮主队列 | 这个桶可以用更小的并发、更大的 TP |
| **按共享前缀排序** | 最大化 prefix cache 命中（见 §5.3） | 多阶段流水线里，system prompt + rubric + few-shot 是固定前缀，收益极大 |

### 4.5 多阶段流水线与背压

我们的实际形态：**原始文本 → question rewriting → answer rewriting → QA 转换（不可验证转可验证）→ 质量特征打标（自包含性 / 矛盾信息 / 假设是否给足）→ verifier/judge**。

各阶段的 token 成本差一个数量级（改写只输出几百 token，answer 生成可能几千，judge 又只输出几十），**直接串起来必然有一个阶段是瓶颈，其余阶段的 GPU 在等**。

两种连接方式，要能说清取舍：

| 方案 | 优点 | 缺点 | 什么时候用 |
|---|---|---|---|
| **内存流式 + 有界队列** | 延迟低、无中间存储成本 | 任一阶段挂了整条链失败；无法只重跑某一阶段；调试困难 | 在线、或阶段极轻 |
| **每阶段独立 job，中间结果落盘（数据集作为边界）** | **可以只重跑改动的那一阶段**；每阶段可独立调并发和资源；中间结果可审计、可复用 | 多一轮 I/O；wall-clock 更长 | **离线几乎永远选这个** |

**强观点（面试可以直接给）**：

> 离线数据 pipeline 的正确切分方式是**每个阶段一个独立 job，中间用持久化数据集做接口**。理由不是优雅——是**重跑成本**。我改了 judge 的 prompt，不应该重新生成一遍 answer。把阶段耦合在一个进程里，等于每次迭代都要付全链路的算力。我们的迭代周期是天级不是季度级，很大一部分就来自这个切分。

**如果必须流式**，背压要显式做：有界队列（满了就阻塞上游）或者 credit-based 流控。**绝不能用无界队列**——它把背压变成 OOM，而且失败时队列里的在途工作全部丢失。

**资源配比**：测出每阶段的 tokens/s 和每样本 token 数，按 `阶段 GPU 数 ∝ 该阶段每样本的 token 成本` 分配。judge 阶段输出短，通常可以和别的阶段共享一个池。

## 5. 成本模型：要能在白板上算出数字 ⭐⭐

### 5.1 基本公式

```
$/M output token = (GPU 单价 $/hr × GPU 数) ÷ (输出吞吐 tok/s × 3600) × 1e6
```

**worked example（70B，8×H100，离线批量）**：

| 项 | 值 | 来源 |
|---|---|---|
| 权重 fp16 | 140 GB | 70B × 2 bytes |
| 可用显存（`gpu_memory_utilization=0.9`） | 640 × 0.9 = 576 GB | |
| **KV 预算** | 576 − 140 = **436 GB** | |
| KV/token | 320 KiB | §3.2 表 |
| **可容纳的 KV token 总数** | 436e9 / 327680 ≈ **1.33 M** | |
| 平均序列 4k → **最大并发序列数** | ≈ **330** | |
| decode step：权重读 | 140 GB / 26.8 TB/s = 5.2 ms | |
| decode step：KV 读（KV 池装满即 436 GB） | 436 / 26.8 TB/s = **16.3 ms** | **注意：长上下文下 KV 读超过权重读** |
| step 合计（含 overhead） | ≈ 22 ms | |
| **理论聚合吞吐** | 330 / 0.022 ≈ **15 k tok/s** | |
| 实际达成（40–60%） | **6–9 k tok/s** | |
| 成本（8 × $2.5/GPU-hr = $20/hr，按 8k tok/s） | **$0.69 / M output token** | |

**这个例子的三个可讲点**：
1. **KV 读在长上下文下超过权重读**，成为 decode 的主瓶颈。这意味着"batching 是免费吞吐"这句话有上限：当 `并发 × 平均长度 × KV/token > 权重字节数` 时（本例约在并发 53 @ 8k 上下文），继续加 batch 的边际吞吐就开始递减。**能说出这个交叉点，比背 continuous batching 强得多。**
2. **input token 比 output token 便宜得多**（prefill 是并行的，decode 是串行的）。用本篇自己的数字算：prefill 2000 token 要 88 ms → **≈ 23 k tok/s**，decode 实际 **6–9 k tok/s**，同一套卡上大约 **3 倍**；并发越低差距越大（batch=1 时 decode 只有 190 tok/s，差两个数量级）。主流 API 的输入/输出定价差也在 **3–5 倍**量级（Claude、GPT 系列当前都是 5 倍）。结论：**设计 pipeline 时"多读文档"比"多生成文本"便宜得多**。
3. **自建 vs 调 API 是一个利用率问题，不是单价问题。** 上面算出的 $0.69/M 已经和同规模模型的 API 报价同量级。所以：**如果你的 GPU 只有 20% 时间在跑，自建成本是 API 的 5 倍。** 自建能赢的三个条件：(a) 长期高利用率，(b) 能吃 spot/碎片算力，(c) 有 API 不给的东西（自定义模型、数据不出域、logprobs）。

### 5.2 量化的收益与代价

| 方案 | 省什么 | 什么时候有效 | 质量代价 |
|---|---|---|---|
| **权重-only INT8/INT4**（GPTQ/AWQ） | 权重显存和读带宽 | **小 batch（memory-bound）收益最大**；大 batch 时收益小，反量化开销甚至可能反噬 | 通常小，但长链推理/数学退化更明显 |
| **W8A8 FP8**（H100 原生） | 显存 + **算力翻倍** | 两头都有收益，H100/H200 上的默认选择 | 一般很小 |
| **KV cache 量化到 FP8/INT8** | KV 显存减半 → **并发翻倍** | 长上下文、高并发场景收益巨大 | 需要在**长上下文**上专门测，短上下文测不出问题 |

**必须说的一句**：量化的质量评估**不能只看 MMLU**。要在**你自己的任务、自己的长度分布**上测。经验上退化最明显的是需要精确多步推理的任务（数学、代码），因为误差会沿推理链累积——而这恰好是我做的数据的类型。所以我的做法是：量化前后跑同一批题的可解率对比，差异超过阈值就不上。

### 5.3 Prefix caching：多阶段 pipeline 的最大杠杆

多阶段 LLM 流水线里，每次调用的前缀几乎完全相同：system prompt + rubric + few-shot 示例（常常 2000+ token），只有末尾的样本内容不同。开 prefix cache（vLLM 的 automatic prefix caching / SGLang 的 RadixAttention）后：

- 命中率 90% 时，prefill 的绝大部分消失。
- **配合按前缀排序调度**（把共享前缀的样本排在一起），命中率能从"随机命中"提到接近上限。

**经典事故（必讲）**：系统提示词里放了一个 `当前时间: 2026-07-29 14:32:11`，或者一个 request UUID，或者一个未排序的 `json.dumps()`——**前缀每次都不同，缓存命中率恒为 0**，而且没有任何报错。排查方法：直接看引擎报的 cache hit rate 指标，如果是 0，去前缀里找变量。

## 6. 可靠性：抢占、恢复、幂等 ⭐⭐⭐

### 6.1 失败分类学（先分类，再谈处理）

| 失败类型 | 频率 | 是容量信号吗 | 处理 |
|---|---|---|---|
| **被抢占**（更高优先级 job 来了） | 共享池里常态 | 是 | 优雅退出 + 检查点 + 重新排队 |
| **OOM** | 自己作的 | 是 | 降并发（AIMD 乘性减）+ 查是不是有超长样本 |
| **引擎崩溃 / CUDA error** | 偶发 | 否 | 重启 worker，在途工作重新入队 |
| **Poison pill**（单条样本必崩） | 稀有但致命 | **否** | 计数，2 次后隔离到 dead-letter |
| **瞬时网络 / 对象存储 5xx** | 常见 | 否 | 指数退避 + jitter 重试 |
| **输出解析失败**（JSON 不合法等） | 常见 | 否 | 有限次重试，仍失败进 dead-letter |
| **静默截断**（撞 max_tokens） | **常见且最危险** | 否 | 见 §9 |

**核心原则**：**容量类失败才触发退避；样本类失败只能隔离，不能退避。** 混淆这两类是自适应并发框架最常见的实现 bug（§4.3 已说）。

### 6.2 检查点粒度：一个可以算的取舍

太细 → 写放大（几百万个小文件，对象存储 LIST 慢到无法续跑）。太粗 → 抢占时丢大量工作。

```
浪费比例 ≈ (检查点窗口 W / 2) / 抢占平均间隔 MTBP
```

要把浪费控制在 5% 以内 → **W ≈ 0.1 × MTBP**。MTBP 40 分钟 → 每 4 分钟落一次盘。

实操上：**按分片写**，一个分片约 5k–10k 个样本或 1–5 分钟的工作量，append-only 写入，写完落一个 manifest 记录该分片包含的 id 范围。续跑时只读 manifest（几千个），不 LIST 几百万个文件。

### 6.3 幂等性与"resume 不可能逐位复现"

- **至少一次投递**：一条样本可能被执行两次（lease 到期、worker 假死后又活了）。写入时按 `sample_id` 去重，后写覆盖先写。
- **诚实的一条**：即使 `temperature=0` + 固定 seed，**continuous batching 下的输出也不是逐位可复现的**——batch 组成变化会改变 kernel 选择和归约顺序，浮点结果在最低位不同，偶尔就翻转一个 token。（社区已有专门讨论批不变性 kernel 的工作。）

  **推论很重要**：resume 的正确性**不能靠"重跑一遍结果一样"来验证**，只能靠 **id 覆盖率**验证——work list 里的每个 id 恰好有一条结果，就算完成。如果你的验收逻辑写成了输出比对，它会一直报假警。

- **优雅退出**：SIGTERM → 停止接新工作 → 让在途请求跑完（或到 grace period 上限就放弃）→ 落盘 → 退出。抢占系统给的 grace period 通常 30–120 秒，**在途请求的最长耗时必须小于它**，否则每次抢占都要丢一批——这反过来约束了 `max_tokens` 的设定。

## 7. 调度：多租户、配额、公平性 vs 利用率

### 7.1 两层配额

| 层 | 语义 | 特性 |
|---|---|---|
| **Guaranteed（保底）** | 每个团队/租户一个不可被抢占的最小份额 | 可预测；但闲置时浪费 |
| **Opportunistic（机会性）** | 保底之外的空闲资源，可被随时抢占 | 利用率高；完成时间不可预测 |

**这就是公平性与利用率的取舍**，可以直接表述：

| 策略 | 利用率 | 可预测性 | 适用 |
|---|---|---|---|
| 严格按团队静态预留 | **低**（各家闲置无法互借） | 高 | 强 SLA、外部客户 |
| 全部可抢占共享 | **高** | 低（job 可能反复重启） | 内部研究、离线 |
| **保底 + 机会性突发** | 高 | 保底部分可预测 | **实践中的正解** |

**关键洞察**：机会性层能不能用，取决于**抢占成本**。抢占成本 = 检查点粒度（§6.2）。所以"能不能高利用率地共享 GPU"这个组织级问题，答案落在一个很工程的细节上——**你的 checkpoint 有多细**。这个因果链在面试里讲出来很有说服力。

### 7.2 其他必须提的调度问题

- **Gang scheduling**：需要 8 卡的 job 必须 8 卡同时拿到，拿到 7 张卡是零价值还占着资源。要 all-or-nothing 分配。
- **碎片化**：池子里散落着 30 张单卡，但没有一个节点有 8 张连着的 → 8 卡 job 永远排不上。需要 bin-packing + 定期 defrag（主动迁移小 job 腾出整节点）。
- **优先级反转**：低优先级的长 job 占着 8 卡，高优先级来了。解法是可抢占 + grace period，但 grace period 又受制于在途请求时长（§6.3）。
- **饥饿**：低优先级 job 被反复抢占，永远跑不完。解法是 **aging**——等待时间越长，有效优先级越高。
- **DRF（Dominant Resource Fairness）**：多维资源（GPU、显存、CPU、网络）下的公平分配概念，知道名字并能说清"按每个租户最紧张的那一维来衡量份额"就够了。

## 8. 监控：报什么、不报什么

### 8.1 在线

| 类别 | 指标 |
|---|---|
| 延迟 | TTFT p50/p95/p99、TPOT p50/p99、端到端 p99 |
| **拆解** | **排队时间**、prefill 时间、decode 时间——**必须分开** |
| 吞吐 | input tok/s、output tok/s、goodput（达标请求/s） |
| 引擎内部 | running / waiting 序列数、**KV cache 利用率**、**抢占/重算次数**、prefix cache 命中率 |
| 资源 | 显存占用、**MFU**（不是 nvidia-smi 的利用率）、网络 |
| 错误 | 5xx 率、429 率、OOM 次数、超时率 |

### 8.2 离线

| 类别 | 指标 |
|---|---|
| 产出 | **goodput（最终入库样本/GPU-hour）**、tokens/GPU-hour、$/M token |
| 进度 | 完成率、**ETA 及 ETA 的漂移量**（ETA 一直后退 = 并发在退化） |
| 并发 | 有效并发 vs 目标并发、AIMD 退避次数 |
| 可靠性 | 抢占次数与恢复耗时、重试率、**dead-letter 计数**、**finish_reason 分布** |
| 流水线 | 各阶段队列深度、各阶段 tokens/s（找瓶颈） |

### 8.3 两条"这个指标在骗你"

1. **`nvidia-smi` 的 GPU 利用率是骗人的。** 它报的是"有没有 kernel 在跑"，不是"算力用了多少"。一个 batch=1 的 decode 循环可以让它显示 100%，而实际 MFU 不到 5%。**要看 MFU 或 tokens/s per GPU。** 这是面试里非常有区分度的一句。
2. **平均延迟是骗人的**（§2 的 M/M/1）。均值 200 ms、p99 5 s 是一个完全正常的（且很糟的）状态。

## 9. 常见失败模式：这个系统最容易在哪里坏 ⭐⭐⭐

| # | 失败模式 | 机制 | 防御 |
|---|---|---|---|
| 1 | **batch 调到 OOM 边缘** | 平时正常，来一个长 prompt → KV 耗尽 → 引擎抢占 + 重算 → 吞吐**非线性崩塌**（thrashing），不是线性下降 | 留 10–20% 余量（`gpu_memory_utilization` 0.85–0.9 而不是 0.98）；监控抢占率而不是等 p99 报警 |
| 2 | **只看均值延迟** | 掩盖排队。ρ=0.9 时排队 = 9× 服务时间 | 报 p99 + **单独报排队时间** |
| 3 | **长 prompt 造成队头阻塞** | 一个 30k token 的 prefill 占住一整个 step，所有 decode 中的序列 TPOT 尖刺 | chunked prefill；或长请求单独分池 |
| 4 | **重试风暴** | 部分故障 → 客户端重试 → 负载在容量下降时反而翻倍 → 全面雪崩 | 重试预算（重试量 ≤ 总流量 10%）、断路器、指数退避 + **jitter**（没有 jitter 会同步成脉冲） |
| 5 | **扩缩容震荡** | 冷启动 3 分钟 > 扩容决策周期 → 扩了没起来又缩 | 按队列深度 + 滞回 + 预热池；短期尖峰用准入控制而不是扩容 |
| 6 | **静默截断（离线，最阴险）** | 撞 `max_tokens` → 输出被切断 → 格式检查可能仍通过（比如 JSON 恰好闭合）→ **一批垃圾数据静默进入训练集** | **必须监控 `finish_reason` 分布**；`length` 的比例突然上升就报警；对截断样本单独标记而不是丢进正常池 |
| 7 | **Poison pill 活锁** | 一条 200k token 的文档 → OOM → 整个 in-flight batch 的工作丢失 → 重试 → 再 OOM，无限循环 | 入队前按 token 数预过滤；硬 `max_model_len`；**每样本失败计数，2 次后隔离到 dead-letter** |
| 8 | **checkpoint 粒度太粗** | 跑到 95% 被抢占，全部重来 | §6.2 的公式：W ≈ 0.1 × MTBP |
| 9 | **prefix cache 被一个动态 token 打死** | system prompt 里的时间戳 / UUID / 未排序 JSON | 监控 cache hit rate；把动态内容全部移到前缀之后 |
| 10 | **AIMD 把样本错误当容量错误** | 一个 poison pill 让并发一路降到 1，job 卡死但不报错 | 严格区分两类错误（§4.3） |
| 11 | **探测与正式跑的采样参数不一致** | 16 条探测用了不同 temperature → 可解率估计有偏 → 筛选逻辑失效，丢错样本 | 探测与正式跑共用同一份 config 对象，禁止分别配置 |
| 12 | **judge/verifier 阶段自身不一致** | LRM-as-judge 在不同题目上对同一标准判得不一致 → 下游筛选噪声大 | 固定 rubric + 抽样人工校准；对同一样本多判几次看方差；judge 的一致性本身要当作监控指标 |

## 10. 10 分钟口述稿

> 我先确认一件事：这是**在线低延迟 serving** 还是**离线批量推理**？这两个的目标函数是相反的——在线优化 SLO 内的 goodput，离线优化每百万 token 的成本，架构选择基本没有重合。我先说这个分叉，再按你想听的那侧展开。
>
> **在线**这侧，一切从一个物理事实出发：prefill 是 compute-bound、decode 是 memory-bandwidth-bound。70B fp16 权重 140 GB，8 张 H100 聚合带宽 26.8 TB/s，所以 decode 一步的下限是 5.2 毫秒，和 batch 多大无关——这就是为什么 batching 几乎是免费的吞吐。做法上：continuous batching 做迭代级调度、PagedAttention 把 KV 分块管理消除碎片、chunked prefill 防止长 prompt 卡住 decode。如果 TTFT 和 TPOT 的 SLO 冲突严重，再考虑 prefill/decode 分池，但要先算 KV 传输成本——2000 token 的 prompt 是 640 MB，400G 网络上 13 毫秒，TTFT 预算几百毫秒才划算。投机解码我会在小并发场景用，大 batch 下它抢算力反而降吞吐。
>
> 指标上我坚持三件事：**报 p99 不报均值**、**排队时间单独度量**、**用 goodput 不用 raw throughput**。排队必须拆出来，因为它区分了"该加卡"和"该修调度器"。而且利用率 0.9 时排队等待就是服务时间的 9 倍，所以在线系统的稳态利用率只能做到 60–70%，那 30% 是买延迟的钱。
>
> **这里我要标一个边界：我没有在线 serving 的 oncall 经验**，机制和容量估算我能推，真实事故复盘我讲不了。我真正做过的是另一侧。
>
> **离线批量**是我在 Reflection 的主责。我们为 RL 合成 math/STEM 数据，跑在共享 GPU 池上，被其他团队抢占是常态。三个设计点：
>
> 第一，**推理预算的分配**。RL rollout 正式跑是每题 128 条，但全对全错的题在 GRPO 里 advantage 为零、没有梯度。所以我们先用 16 条探测可解率，全对全错的直接丢。盈亏平衡点可以算：16 除以 128 是 12.5%，只要丢弃率超过 12.5% 就净赚，我们实际在 40% 量级。这和 DAPO 的 dynamic sampling 是一个思想。要注意 16 条的统计精度有限——全对时可解率的 95% 下界只有 0.83，所以我们其实在丢一部分有信号的题，这是显式取舍不是免费的。
>
> 第二，**自适应并发**。共享池里可用容量是别人的函数，固定并发不是欠打就是持续 OOM。我们做了 TCP 式的 AIMD：成功就加一、失败就砍半，加 jitter 防羊群。最关键的实现细节是**必须区分容量类失败和样本类失败**——429 和抢占要退避，但单条样本 prompt 超长导致的失败不能退避，否则一个 poison pill 就能把并发压到 1、整个 job 卡死不报错。这是我们踩过的坑。
>
> 第三，**抢占恢复**。检查点粒度有公式：浪费比例约等于窗口的一半除以抢占平均间隔，要控制在 5% 就取 MTBP 的十分之一。样本 id 按内容加配置哈希，写入按 id 幂等，续跑靠 id 差集。有一点要诚实：continuous batching 下即使 temperature=0 输出也不是逐位可复现的，因为 batch 组成会改变归约顺序——所以 resume 的验收标准只能是 **id 覆盖率**，不能是输出比对。
>
> **成本**上我会算给面试官看：8 卡 H100 跑 70B，KV 预算 436 GB、每 token 320 KB，能装 133 万 token，4k 上下文下并发约 330，实际吞吐 6–9k tok/s，二十美元一小时算下来大约 0.7 美元每百万输出 token。这个数和 API 报价同量级——**所以自建能不能赢是利用率问题不是单价问题**：利用率 20% 的话自建是 API 的五倍贵。
>
> 最后是**最容易坏的地方**：batch 调到 OOM 边缘会 thrashing 式非线性崩塌，不是线性变慢；离线最阴险的是撞 max_tokens 的静默截断，格式检查还能通过，一批垃圾就进训练集了——所以 finish_reason 的分布必须监控。还有一个反直觉的：nvidia-smi 的 GPU 利用率是骗人的，它只报有没有 kernel 在跑，要看 MFU 或者 tokens/s per GPU。

## 11. 面试前一页速记

**第一句**：先分叉——在线（p99 / goodput）vs 离线（$/M token）。目标函数相反，架构不同。

**物理地基**：prefill = compute-bound；decode = memory-bound。70B/8×H100 decode step 下限 = 140 GB ÷ 26.8 TB/s = **5.2 ms**，与 batch 无关 → batching 近乎免费的吞吐。

**KV 公式**：`2 × layers × kv_heads × head_dim × dtype_bytes` per token。**70B GQA = 320 KiB/token；8B = 128 KiB；同规模 MHA = 2.5 MiB（8 倍）。**

**交叉点**：当 `并发 × 长度 × KV/token > 权重字节` 时，KV 读超过权重读，batching 的边际收益开始递减（70B @ 8k 约在并发 53）。

**在线四件套**：continuous batching（收益来自长度方差）／PagedAttention（碎片 60–80% → <4%）／chunked prefill（防 TPOT 尖刺）／PD 分离（先算 KV 传输：640 MB / 13 ms）。

**投机解码**：用算力换带宽。**小 batch 赚、大 batch 亏**。分布等价（拒绝采样）。

**并行顺序**：能单卡就 DP 多副本 → 节点内 TP（取放得下的最小度）→ 跨节点 PP（吞吐）。PP 在 decode 有气泡。

**冷启动 2–5 分钟** → 不能靠扩容应对分钟级尖峰 → 预热池 + 按队列深度 + 滞回 + 准入控制降级。

**离线三件套**：① 16 条探测筛选，盈亏平衡 = 16/128 = **12.5% 丢弃率**；② **AIMD**（+1 / ×0.5，加 jitter），**必须区分容量类失败与样本类失败**；③ 检查点窗口 **W ≈ 0.1 × MTBP**。

**流水线**：每阶段独立 job + 数据集做边界（理由 = 重跑成本，不是优雅）。必须流式则用有界队列，**绝不用无界队列**。

**成本**：`$/M = (GPU$/hr × N) / (tok/s × 3600) × 1e6`。70B/8×H100 ≈ **$0.7/M output**。input 比 output 便宜约 3×（低并发时更多），API 定价差 3–5×。**自建 vs API 是利用率问题。** 批量 API 打 5 折（1h 典型 / 24h 上限）就是延迟的市场定价。

**监控红线**：p99 + **排队时间单独拆**；抢占/重算率；KV 利用率；**finish_reason 分布**；goodput。

**两个骗人的指标**：nvidia-smi 利用率（只报有没有 kernel）、平均延迟（ρ=0.9 → 排队 9×）。

**必背句**：在线系统里，你为峰值买单却按均值收益；离线系统没有峰值，所以它的正解恰是在线的禁忌。

**诚实边界**：没有在线 serving 的 oncall 经验，能推演不能复盘；离线批量是我的主场。

## 12. 常见追问 + 应答要点

1. **「怎么决定 batch size？」** 不是调一个数，是设一个**显存预算**加一个**SLO 约束**。离线：`gpu_memory_utilization` 0.85–0.9，`max_num_seqs` 设到 KV 预算算出的上限，剩下交给 continuous batching 动态填。在线：从 SLO 反推——目标 TPOT 决定 step time 上限，step time 决定并发上限。**永远留 10–20% 余量**，因为 OOM 边缘的失效是非线性的（抢占 thrashing）。

2. **「p99 突然涨了，怎么排查？」** 按拆解顺序：先看**排队时间 vs 服务时间**——排队涨说明容量不足或调度不公；服务时间涨再往下分 prefill 和 decode。decode 变慢看**并发数是不是涨了**（KV 读变多）和**抢占率**；prefill 变慢看是不是来了长 prompt（看 prompt 长度分布的 p99）。最后才看硬件（ECC、降频、网络）。**顺序很重要**，先看拆解再看硬件。

3. **「加机器能解决吗？」** 取决于瓶颈在哪。排队时间主导 → 能。单请求 decode 慢（TPOT）→ **不能**，加副本不会让单个 token 更快，那要靠减小 TP 通信、量化、投机解码或换更小的模型。这个区分是判断"是容量问题还是延迟问题"的关键。

4. **「离线 job 跑到 90% 挂了怎么办？」** 不应该重来。id 按内容哈希、结果 append-only 按分片写、manifest 记录已完成 id，续跑 = 差集。检查点窗口按 `0.1 × MTBP` 定。验收标准是**id 覆盖率**不是输出比对——因为 continuous batching 下输出不逐位可复现。

5. **「怎么防止一个坏样本搞死整个 job？」** 三层：入队前按 token 数预过滤 + 硬 `max_model_len`；每样本失败计数，超过 2 次隔离到 dead-letter 而不是重新入队；**AIMD 不把样本类失败当容量信号**。第三条最容易漏，漏了会表现为"job 没报错但一直不动"。

6. **「量化能省多少？什么时候不该用？」** 权重-only INT4 在**小 batch**（memory-bound）收益最大，大 batch 时反量化开销可能吃掉收益；FP8 在 H100 上两头都赚。KV 量化能让并发翻倍，对长上下文最划算。**不该用的情况**：任务需要长链精确推理（数学、代码）且没有在自己的分布上验证过——退化会沿推理链累积，MMLU 上看不出来。

7. **「多租户怎么保证公平又不浪费？」** 保底配额（不可抢占）+ 机会性突发（可抢占）。**机会性层能不能用，取决于抢占成本，而抢占成本 = 检查点粒度。** 再加 gang scheduling（避免拿到 7/8 卡）、bin-packing 防碎片、aging 防饥饿。

8. **「在线和离线能共用一个集群吗？」** 可以，而且是提高利用率的主要手段：离线跑在在线的空闲容量上，作为**可抢占的低优先级**。前提是离线侧必须有完备的 pause/resume，否则在线一扩容就把离线打断，离线永远跑不完。**这正好是我做的那套框架的价值所在**——它是"共享集群"这个组织决策的技术前提。

9. **「MoE 有什么不同？」** 权重总量大但每 token 激活的少 → 显存吃紧但算力相对宽松，更 memory-bound。需要专家并行（EP）+ all-to-all 通信，而且**负载不均**：热门专家成瓶颈。批量场景可以按路由结果重排来提高专家局部性。（诚实说明：我没有专门做过 MoE 的 serving 优化。）

10. **「怎么估算需要多少 GPU？」** Little's Law 正着用和反着用。在线：`并发 = QPS × 平均请求时长` → 并发 × 平均长度 × KV/token = 需要的 KV 显存 → 加上权重 → 除以单卡显存 = 卡数。离线：`总 token 量 / 目标吞吐 / 3600 = GPU-hour`，再除以 deadline 得并行度。**关键是把这个算式说出来**，具体数字面试官不会核对，但会看你有没有这个框架。

11. **「输出长度不可预测，怎么做容量规划？」** 用历史分布而不是最大值。KV 按 p50 长度做并发规划，按 p99 长度留抢占余量。离线可以按预估长度分桶（预估错了有兜底：超时的样本移到长桶重跑）。**永远不要按 max_tokens 做显存规划**——那是 PagedAttention 出现之前的做法，会浪费 60–80%。

12. **「你怎么知道你的自适应并发是对的，而不是刚好瞎撞对了？」** 三个证据：(a) 有效并发应该随着共享池空闲度变化而变化，如果它是条直线说明控制器没生效；(b) 抢占/429 率应该稳定在一个低水位而不是零——**恒为零说明太保守了，在欠打**；(c) 对照实验：固定并发 vs AIMD，同一批工作比 wall-clock 和失败次数。第 (b) 条最能说明你理解 AIMD 的本质——它是要主动探到边界的。

13. **「如果只给你一半的 GPU，你砍什么？」** 优先级顺序：先砍**质量筛选之外的重复采样**（128 → 64，看 reward 曲线掉多少）；再开 FP8 和 KV 量化；再提高前置筛选比例（用更多探测换更少全量）；最后才砍数据总量。**不砍**：检查点和幂等（那是可靠性不是性能）、finish_reason 监控。

| **§4.3 AIMD ⭐⭐⭐** | 自建 pause/resume 框架、动态申领/让出资源、TCP 式自适应并发 | 重点讲"**区分容量类失败与样本类失败**"这个踩过的坑——这是真做过才会有的细节 |
| **§4.5 流水线背压** | 多阶段 LLM 流水线：question rewriting → answer rewriting → QA 转换（不可验证转可验证） | 讲"每阶段独立 job + 数据集做边界"的理由是**重跑成本**，以及各阶段 token 成本差一个量级 |
| **§6 抢占恢复 ⭐⭐⭐** | pause/resume 框架 | 检查点粒度公式 + id 幂等 + "resume 只能验 id 覆盖率不能验输出" |
| **§7 多租户** | 共享池的实际竞争经验 | 讲"机会性层能不能用取决于检查点粒度"这条因果链 |
| **§9-6 静默截断** | 手动检查 trace 发现学习行为异常（格式化推理、失控推理、错误推理、reward hacking） | 迁移过来：**我的习惯是手动读原始 trace，不是只看聚合指标**——静默截断这类问题只有读 trace 才能发现 |
| **§9-12 judge 不一致** | LRM-as-judge 在不同题目上对同一标准判得不一致 | 这是一手观察，讲"judge 的一致性本身要当监控指标"很有说服力 |
| **§2 / §9 "指标在骗你"** | Anthropic take-home：证明 ROUGE 在预测不安全回复上 AUROC 只有 0.569（≈掷硬币），自建 claim 级 grounding grader 达 0.844，置信区间不重叠；137 对扰动测试套件分层报检出率；两个 refuted prior 如实写进报告 | 迁移成方法论：**"我的默认动作是先验证指标本身是不是在测它声称在测的东西"**——nvidia-smi 利用率、平均延迟、raw throughput 都属于这一类 |
| **成本/取舍的严谨性** | Decagon 备战项目：手写 reverse-KL on-policy distillation、过程奖励 vs 结果奖励对照实验、四个实测踩到的坑 | 用来证明"我会做对照实验而不是背结论"，可放在量化那节 |
| **Meta 经历** | Instagram Reels / Facebook Feed 推荐建模；内部数据分析 agent（多 agent 采样表格 → sandbox 写代码分析 → 综合假设供下轮线上实验） | 推荐系统那段可以支撑"大规模在线系统的指标直觉"，但**不要说成 LLM serving 经验**；数据分析 agent 那段可以支撑"多阶段流水线设计" |
| **不能碰的** | 金融/交易、在线 serving oncall、MoE serving 优化、多模态 | 直接说没做过，然后给出"我会怎么验证"的路径 |

### 三句可以直接背的诚实边界话术

1. **在线 serving**：「在线这侧我是从引擎实现和论文层面理解的，容量和成本我能现场推；但我没背过在线 pager。要听真实事故复盘的话，我能讲的是离线批量侧的——共享池抢占导致 job 反复重启、以及我们怎么用自适应并发把它稳住。」
2. **具体引擎版本细节**：「vLLM/SGLang 的具体版本行为我不敢打包票，这类东西迭代太快。我确定的是机制层面的取舍——比如 KV 抢占是重算还是 swap、chunked prefill 解决什么问题。落地前我会先跑一遍基准测出来，而不是引用一个可能过期的数字。」
3. **MoE / 多模态**：「我没做过 MoE 的 serving 优化，也没有多模态经验。MoE 我知道它更 memory-bound、需要 EP 和 all-to-all、以及专家负载不均是主要问题，但我没有一手的调优经验，这块我会先做基准而不是先给方案。」
