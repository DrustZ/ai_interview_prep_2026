## 0. 这篇解决什么 · 和其他文件的边界

题面：**"Design a benchmark for evaluating agents."**

这是一道**测量系统设计题**，不是模型设计题。交付物不是一个更强的 agent，而是一台**能稳定分辨两个 agent 谁更强、并且能说清自己误差有多大的仪器**。绝大多数候选人会把它答成"我要评哪些能力维度"——那是需求清单，不是系统设计。区分度、噪声下界、可复现性、抗污染、单次评测成本，这五件事才是本题的主体。

## 1. 先问清楚：七个澄清问题 ⭐⭐⭐

每个问题后面标注的是**这个答案会改掉哪个设计决策**——面试时要把这句说出来，否则会被当成拖时间。

| # | 问题 | 答案改变什么 |
|---|---|---|
| 1 | **这个 benchmark 服务谁的决策？** 是"选一个基座模型"、"决定这次训练要不要上线"、还是"对外发榜"？ | 决定**噪声预算**。上线 gate 要能分辨 2–3pt（→ 配对设计 + 大 k + 大题量）；选型只要分辨 10pt（→ 300 题跑一次就够）；对外发榜则**私有 held-out 集变成必需品**（§8）。 |
| 2 | **被测对象是模型还是系统？** 换 scaffold 算不算换了被测对象？ | 决定 harness 是自变量还是常量。Terminal-Bench 上同一模型换 scaffold 差 15–20pt——如果没锁死这一层，所有对比都不成立。 |
| 3 | **agent 有写权限吗？会花钱/发消息/改真实数据吗？** | 决定沙箱等级和"是否需要 undo"。只读 agent 可以打真实 API；有写操作必须全部快照 + 回滚，而且要专门测"该拒绝时拒不拒绝"。 |
| 4 | **任务的正确性谁说了算？** 有没有可程序化的终态？还是必须人判？ | 这是**最硬的约束**（§6）。没有程序化 verifier 的领域，benchmark 规模上限直接从 1000 题掉到 100 题，成本高一个数量级。 |
| 5 | **产品允许重试吗？有没有廉价 verifier 可以 rerank？** | 决定报 pass@k 还是 pass^k（§7）。coding agent 有测试可以重试 → pass@k 有意义；退款 agent 一次做错就是真赔钱 → 只能看 pass^k。 |
| 6 | **一次完整评测的预算是多少（$ 和 wall-clock）？** | 决定 $N_{task} \times k \times steps$ 的三方分配（§10）。"每次 commit 都跑"和"每个 release 跑一次"是两个完全不同的设计。 |
| 7 | **这个 benchmark 要活多久？谁维护？** | 决定要不要程序化生成任务。一次性评估可以手写 200 题；要活两年就必须有滚动换题机制和 verifier CI，否则 12 个月后它会静默失效（§9）。 |

补充第 8 问（如果时间允许）：**现在用什么在做决策？** 如果已有一个内部 eval，先问它的 test-retest 噪声是多少——很多团队从没测过，这个问题本身就能拿分。

## 2. 指标先于方案：benchmark 自己怎么算成功 ⭐⭐⭐

这一节是本题和普通 eval 题的分水岭。**benchmark 的指标不是 accuracy，是"这台仪器好不好用"的元指标。**

### 2.1 七个元指标

| 元指标 | 定义 | 怎么量 | 不合格的样子 |
|---|---|---|---|
| **区分度** | 能分开真实能力不同的两个系统 | 取已知强弱对（大 vs 小模型、给工具 vs 不给工具、当前版本 vs 上季度版本），看分差 | 所有被测对象都 95% 或都 5% |
| **噪声下界 (test–retest)** | 同一系统重跑两次的分差 | 同一 checkpoint、同一配置跑两轮，看 $\lvert\Delta\rvert$ 的分布 | 噪声带宽 > 你要检测的效应量，此时整个 benchmark 不可用 |
| **可复现** | 半年后 / 另一台机器上能否重跑出同一个数 | 冻结镜像重跑历史版本 | 依赖漂移、时间漂移（§9） |
| **与线上相关性** | 离线名次能否预测线上结果 | 已上线的 N 个版本：离线分 vs 线上指标的秩相关 $\rho$ | $\rho$ 接近 0 时这个 benchmark 是装饰品 |
| **抗污染** | 训练集里含它时分数虚高多少 | public 与私有配对集的分差（§8） | 差 20pt 却仍在拿 public 分做决策 |
| **成本** | 一次完整评测的 $ 与 wall-clock | 直接测 | 一次跑 5 天 → 没人会在做决策前跑它 |
| **可诊断** | 失败能不能定位到原因 | 失败分类的分布，以及 infra failure 是否被单独计 | 只有一个总分 |

**先测噪声，再定题量。** 顺序反了的话，你会造出一台看起来很精密、但读数抖动比信号还大的仪器。

### 2.2 样本量算术（这个数字要能当场算）

未配对比较两个系统，每题跑一次，成功率 $p$，题量 $n$：

$$\mathrm{SE}(\Delta p) \approx \sqrt{\frac{2p(1-p)}{n}}$$

$p=0.5$、$n=500$ → SE ≈ 3.2pt → 80% power 下能可靠检测的差异约 $2.8 \times \mathrm{SE} \approx 9$pt。

配对设计（同一批任务上比两个系统，用 McNemar 或配对 bootstrap）：有效方差只由**不一致对**贡献。不一致率 $d=0.2$、$n=500$ → SE $\approx \sqrt{0.2/500} = 2.0$pt → 可检测约 5pt。

**如果每题只跑一次，agent 的 run-to-run 方差会整个进到 SE 里**，上面两个数字还要恶化。

> **高分句**：一个 500 题、每题跑一次的 agent benchmark，分辨不了 2 个点的差距——公开榜单上前三名彼此在噪声之内是常态。所以我的报告里主指标永远带 bootstrap 置信区间，模型对比永远用配对检验而不是排名。

### 2.3 明确不能用的指标

| 不能用 | 为什么 |
|---|---|
| **单一总分** | 掩盖分层。总分 72% 里可能"写操作类任务只有 30%"，而写操作正是唯一会造成真实损失的那类。 |
| **pass@1 当发布 gate** | 它测的是单次的平均能力，不测一致性，因而不测可部署性。$p=0.7$ 的系统连续 8 次全对只剩 5.7%（§7）。 |
| **轨迹与人类示范的相似度** | 路径不唯一。这个指标会惩罚比人更聪明的解法（一次批量查询代替三次单查），奖励模仿。 |
| **LLM judge 的平均分做主 gate** | judge 偏差会被 agent 直接优化掉。主流 agent benchmark 刻意回避 judge 当主判分，这点值得主动说。 |
| **与人类偏好的相关性** | 在 agent 场景它奖励的是"总结写得漂亮"，而不是"数据库里那笔退款金额对不对"。 |

这里可以引一个我自己做过的实证（Anthropic take-home，医疗域，可公开讲）：**ROUGE 在"预测医生标注的不安全回复"这个任务上 AUROC 只有 0.569，基本等于掷硬币；换成自建的 claim 级 grounding grader 是 0.844，两个置信区间不重叠。** 这件事的迁移含义是——**一个看起来天经地义的自动指标，可能和你真正关心的量几乎无关，而且这件事是可以在两天内证伪的**。造 agent benchmark 时第一件该做的事，就是拿人工标注给自己的自动 verifier 算一次 AUROC / 检出率，而不是默认它对。

## 3. agent 评测为什么比单轮 LLM 评测难 ⭐⭐⭐

不要泛泛说"因为多轮"。要说清每个结构差异各自逼出什么设计——口述时先讲前四条（多步 / 有状态 / 有副作用 / 路径不唯一），后三条是它们的连带后果。

| 维度 | 单轮 LLM eval | agent eval | 逼出的设计后果 |
|---|---|---|---|
| **多步** | 1 步 | 10–100 步 | 误差累积 + 信用分配。终态成功率无法区分"每步都准"和"错了能救回来"。→ 必须加 **recovery rate** 和 **step budget 曲线** |
| **有状态** | 样本独立同分布 | 第 $t$ 步改变第 $t+1$ 步的输入分布 | 不能把步当独立样本做统计；每题必须从干净快照启动；**reset 速度直接决定你能负担多大的 $k$** |
| **有副作用** | 无 | 写库、发邮件、花钱、删文件 | 沙箱 + 回滚是基础设施而不是加分项；评测本身可能造成损害；真实外部调用在 eval 模式下必须**硬失败**而不是静默 mock |
| **路径不唯一** | 输出可枚举 | 多条正确路径，且可能存在**不该走通的捷径** | 过程评分必须写成**约束满足**而不是**脚本匹配**（§4.3） |
| **评分者形态** | 参考答案匹配 | 终态比对 + 约束断言 + 环境探针 | verifier 变成一套需要自己被测试的软件（§5.5） |
| **方差来源** | 只有采样温度 | 采样 × 环境随机 × user simulator × 外部服务 | 必须多次运行，且必须能把方差归因（§7.3） |
| **成本** | 一次 forward | $steps \times tokens \times k$ | 采样策略本身成为设计的一部分（§10） |

### 误差累积的算术锚点（背下来）

| 单步可靠性 | 20 步 | 30 步 | 50 步 |
|---|---|---|---|
| 0.99 | 0.82 | 0.74 | 0.61 |
| 0.98 | 0.67 | 0.55 | 0.36 |
| 0.95 | 0.36 | 0.21 | 0.08 |

反过来读更有用：**要让一个 20 步任务的成功率达到 90%，单步可靠性需要 99.5%。** 而真实 agent 的单步可靠性远达不到——它们靠的是**出错后能观察到错误并纠正**。所以：

> **高分句**：终态成功率把"每步都对"和"错了能救回来"压成了同一个数字，但这两者在生产里完全不同——后者才是真正的鲁棒性。所以我会在 benchmark 里显式注入故障（工具返回 500、返回空结果、返回过期数据），单独报一条 **recovery rate**：给定第 $i$ 步收到异常，agent 后续把任务拉回成功的比例。

这条"注入故障测恢复"是很多候选人不会说的，而它同时解决了两件事：测到了恢复能力，也把环境随机性变成了**可控且可归因**的随机性（§5.1）。

## 4. 过程 vs 结果 ⭐⭐⭐（本题核心）

### 4.1 只看终态成功率会漏掉的四类情况

| 类型 | 具体形态 | 为什么危险 |
|---|---|---|
| **① 蒙对**（right answer, wrong reason） | 暴力枚举、直接构造目标 URL 跳过流程（WebArena 实测被 exploit）、读 `.git` 历史拿 gold patch（SWE-bench Pro 实测抓到） | 终态对，能力为零。换一个同类任务立刻崩，但 benchmark 给了满分 |
| **② 绕过约束达成目标** | 退款流程跳过身份验证，但退款单确实创建了 | **终态和正确行为完全不可区分**。这是最危险的一类 |
| **③ 代价不可见** | 达成目标但调了 80 次工具、烧了 40 美元、顺手删掉了别的文件（pass-to-pass 测试不覆盖的部分） | 在真实系统里这是事故，在 benchmark 里是满分 |
| **④ 过程对但结果错**（假阴性） | 全部步骤正确，最后一步撞上外部服务 5xx；或 verifier 的字符串匹配没匹上 | 被记成能力缺陷，实际是环境/评分器缺陷。会把改进方向带偏 |

①②③ 是**假阳性**，④ 是**假阴性**。只报一个终态成功率的 benchmark，这四类全部不可见。

### 4.2 一个我自己跑出来的实证 ⭐⭐⭐

在近期自建的 Decagon 备战项目里（`projects/decagon_finetune/levels/level5_process_reward/`），我把"过程 vs 结果"做成了一个可执行的对照实验。场景是退款的五步流程 `verify_identity → lookup_order → check_return_window → check_prior_refund → issue_refund`，额度上限 \$500，共 153 条轨迹分五类：

| 轨迹类型 | 违规 | n | final_only | final + efficiency | process_reward |
|---|---|---|---|---|---|
| compliant | 否 | 70 | **1.000** | 0.750 | +12.0 |
| incomplete | 否 | 18 | 0.000 | −0.114 | +2.3 |
| skip_step | **是** | 26 | **1.000** | **0.800** | −17.0 |
| wrong_order | **是** | 24 | **1.000** | 0.750 | −16.0 |
| over_refund | **是** | 15 | **1.000** | 0.750 | −8.0 |

两个结论，第二个才是杀手锏：

1. **只看结果时，合规与三种违规完全平局**（全是 1.000）。这不是"区分度不够"，是**零区分度**——benchmark 对合规这件事完全失明。
2. **一旦叠加任何效率项，违规就严格胜出。** 每次工具调用扣 0.05 之后，`skip_step` 得 0.800，`compliant` 只有 0.750。跳过校验少调一次工具、同样拿到退款，**净赚**。

> **高分句**：现实中没有"纯粹只看结果"的评测——总会叠一个延迟项或成本项，因为没有哪个生产系统对延迟和成本无感。而"结果 + 效率"这个组合会主动把最高分发给绕过合规的 agent。这就是为什么过程约束必须是一个独立的**否决维度**，而不是总分里的一个加权项。

第三个容易被忽略的区分：**`incomplete`（没做完，也没违规）不能和 `skip_step`（做错了）同等处理。** 如果 benchmark 把两者都记成"失败"，被优化的 agent 会学成"宁可什么都不做"——那是另一种失败模式。所以判分要三分类：

```
success       终态达成 且 无硬约束违规
incomplete    终态未达成 且 无违规      ← 扣分
violation     任何硬约束被破坏           ← 无论终态如何，整题判负
```

### 4.3 过程评分的四种实现（按可靠性排序）

| 方式 | 怎么做 | 可靠性 | 可被 game 吗 | 维护成本 |
|---|---|---|---|---|
| **必经点断言** | 任务定义里声明 `must_call` / `must_not_call` / 顺序约束 / 参数约束，从 trace 程序化检查 | 高（确定性） | 中：agent 会"调了但不看返回值" | 每任务几行 |
| **中间状态比对** | 关键步之后对环境快照做断言 | 高 | 低 | 需要环境支持细粒度快照 |
| **反事实探针** | 改一个前提（订单已过退款窗口），看行为是否随之改变 | **最高，专治"蒙对"** | 极难 | 要成对造题 |
| **rubric / LLM judge 读 trace** | 判"是否核实了身份"这类语义条件 | 低–中 | 容易 | 最低 |

**反事实探针值得单独展开**，它是本节最有区分度的设计：

它绕开了"路径不唯一"这个根本困难——不检查 agent 走了哪条路，只检查它的**行为是否对关键前提敏感**。造一对任务，除了"订单是否在退款窗口内"这一个变量外全部相同：

- 真正执行了 `check_return_window` 的 agent：A 退款，B 拒绝。
- 跳过校验直接退款的 agent：A、B 都退款——A 判对、B 判错，**终态指标上它照样能拿到这一对里一半的分；但在配对差分上它得 0，因为它的行为对关键前提完全不敏感。**

> **高分句**：单个样本的绝对分数没法区分"会做"和"蒙对"，**成对任务的行为差分**才是能力证据。

这和我在 Anthropic take-home 里做的 **137 对扰动测试套件**是同一个思想：不看单样本绝对分，看扰动前后的行为差分，并且**按扰动类型分层报检出率**——因为总的检出率会掩盖"对某一类扰动完全无感"这种致命缺口。同一套方法直接可以搬到 agent benchmark 上。

### 4.4 过程分为什么不能当主分

三条理由，面试里要主动说，否则会被追问打回：

1. **路径不唯一**：任何"必须按这个顺序调这几个工具"的评分都会惩罚更优的解法。**所以断言要写成约束（`verify_identity` 必须在 `issue_refund` 之前完成）而不是脚本（第 1 步必须是 `verify_identity`）。**
2. **过程分自己会被 game**：`must_call` 里有 `verify_identity`，agent 就学会调用它然后忽略返回值。防御是把断言绑定到**数据流**上——`issue_refund` 的 `order_id` 必须来自上一步 `lookup_order` 的返回值，而不是凭空生成；再配上反事实探针交叉验证。
3. **过程分需要人来定义**，因此覆盖不全。硬约束能穷举（政策条款是有限的），"好的解题路径"不能。

**最终结构：结果作 gate，过程作否决项与诊断维度，两者不做加权求和。**

推荐的每题输出（而不是一个标量）：

```text
verdict:        success | incomplete | violation | infra_failure
violations:     [skipped_verify_identity, over_limit_refund, ...]
cost:           steps, tool_calls, input/output tokens, $, wall_clock
robustness:     injected_fault_recovered: true/false
counterfactual: paired_task_id, behavior_changed: true/false
```

> **高分句**：过程分不是给成功的 agent 加分用的，是给"看起来成功"的 agent 减分用的。

## 5. 环境设计 ⭐⭐⭐

### 5.1 确定性 vs 随机性：三档，不是两档

| | 全确定 | **受控随机** | 真实随机 |
|---|---|---|---|
| 形态 | 冻结镜像 + 固定 seed + 全 mock | 固定 seed 的 user simulator、按 schedule 注入的故障 | 打真实网站 / 真实第三方 API |
| 优点 | 可复现、可 debug、方差只来自模型 | 能测鲁棒性与恢复，且方差**可归因** | 保真度最高 |
| 代价 | agent 会过拟合到环境怪癖；测不到恢复能力 | 故障分布本身要设计和辩护 | 不可复现、有真实副作用、分数随时间漂移 |
| 用在哪 | 回归 CI、模型间比较 | **能力评估主集** | 上线前的小规模保真度校准（20–50 题） |

**核心判断：方差要么消除，要么可归因，不能既存在又不可控。** 落地做法是把所有随机源做成显式参数并写进 run manifest：

```text
run_manifest: {
  image_digest, dep_lockfile_hash, harness_version, model_id+version,
  env_seed, user_sim_seed, user_sim_model, fault_schedule_id,
  frozen_clock, step_budget, temperature, tool_schema_version
}
```

有了这个，任何一次失败都能**精确重放**。没有这个，"这题为什么挂了"要花半天，而这半天会重复几百次。

### 5.2 可复现的四层（一层都不能少）

| 层 | 具体做法 | 漏掉会怎样 |
|---|---|---|
| **依赖** | 容器镜像锁 digest（不是 tag）；lockfile 到 hash；网络默认 deny | 三个月后同一个 commit 跑出不同分数，且没人知道为什么 |
| **状态** | 每题从快照启动、跑完销毁；用 copy-on-write（docker layer / btrfs snapshot）让 reset 是秒级 | reset 要 2 分钟的话，$N \times k = 4000$ 次 rollout 光 reset 就是 **133 机时**（串行 5.5 天，并行 32 路也要 4 小时纯等待） |
| **时间** | 冻结系统时钟（`libfaketime` 之类），任务描述用相对时间 | "查最近 7 天的订单"这类任务的正确答案会随日历静默改变——这是最隐蔽的漂移 |
| **随机** | 所有 seed 显式记录；judge 若用 LLM 则固定版本 + temperature=0 + 多次投票 | pass^k 里混进了 harness 的方差（§7.3） |

### 5.3 沙箱与副作用隔离

- **网络默认关闭**，需要的外部内容做本地录制回放（VCR / WARC 快照）。这不只是复现性问题——**联网的 agent 可以直接搜到答案**，这是污染的运行时形态（§8）。
- **资源上限**：CPU / 内存 / 磁盘 / 进程数 / wall-clock。防 fork bomb，也防 agent 用"跑 10 万次暴力枚举"换成功率。
- **环境卫生 checklist**（每条都有真实先例）：
  - [ ] strip `.git`（SWE-bench Pro 抓到模型读 git 历史直接取 gold patch）
  - [ ] 评分用的测试文件在评分阶段才挂载，agent 阶段不可见
  - [ ] 答案不能出现在注释、README、日志、fixture 里
  - [ ] verifier 的代码和数据 agent 不可写（否则 agent 会改测试）
  - [ ] 环境里不能有指向公开题库的 URL
- **真实副作用必须硬失败**：eval 模式下调用真实支付/发信接口应当抛错并记为 `unsafe_action`，**而不是静默 mock 成功**。静默 mock 会让你永远测不出 agent 是否敢做危险动作。

### 5.4 user simulator：既是噪声源也是被攻击面

多轮 agent 必须有一个模拟用户，而它是 benchmark 里**方差最大且最容易被忽视**的组件。

| 问题 | 表现 | 做法 |
|---|---|---|
| 方差 | 同一任务重跑就挂，根因是对话分支敏感 | 固定 simulator 模型版本 + seed；给剧本约束（persona、已知信息、**不能主动透露的信息**） |
| 被诱导 | agent 说服 simulator 偏离剧本，或直接问出答案 | simulator 的系统提示里写死"你不知道 X"；对 simulator 输出做泄漏检测（gold 关键字出现即判该 run 无效） |
| 判分权错配 | simulator 说"我满意了"就算成功 | **simulator 绝不持有判分权**，判分只看环境终态 |
| 同源偏差 | simulator 和被测 agent 同一个模型 → 相同的误解会互相配合 | 用不同 family 的模型做 simulator，并做一次交叉检验（换 simulator 模型看排名是否稳定） |

### 5.5 verifier 自己是未经测试的软件 ⭐⭐⭐

这是面试里最能体现"真做过 eval"的一段。两个公开证据：

- OSWorld 原版 369 题里 **~10% 的任务本身是坏的**（评分脚本失效、依赖挂了），所以才有了 OSWorld-Verified。
- SWE-bench Pro 的第三方审计发现 grader **约 1/3 试次误判**（错收 8.5%、错拒 24%）。

一个 500 题的 execution-based benchmark，它的评分逻辑就是 **500 个小程序**。没有测试的 500 个小程序会坏，这是常识。所以：

```text
每个任务必须附带:
  gold_trajectory        人工或强模型跑通并经人工确认 → verifier 必须判过
  known_bad_trajectory   至少 1 条（跳步 / 越权 / 假成功）→ verifier 必须判不过
  last_verified_at       时间戳 + owner
CI: 每日在 gold / known-bad 上重跑 verifier，任何一条翻转即告警
```

> **高分句**：verifier 是 benchmark 里唯一没人评测的组件。我会给每个任务配一条 gold 轨迹和一条已知坏轨迹当单元测试——这一步的成本大概是任务制作成本的 20%，但它是 OSWorld 和 SWE-bench Pro 两次公开翻车的根因。

## 6. 任务来源与可验证性 ⭐⭐⭐

### 6.1 三种来源的取舍

| 来源 | 怎么拿 | 优点 | 坑 | 建议占比 |
|---|---|---|---|---|
| **真实任务采集** | 生产 trace / 工单 / PR 历史 / 内部工具日志，脱敏后重建初始状态 | 分布真实、难度真实、可辩护 | 隐私；**初始状态重建是最大障碍**（真实系统状态有脏数据、重名实体、历史遗留字段）；只包含"人做过的事" | 50–70% |
| **半合成**（真实种子 + LLM 改写） | 取真实任务，改参数、加干扰项、造反事实配对 | 可控扩量；**反事实对只能这样造** | 改写会漂出真实分布；容易改出不可解题 | 20–40% |
| **全合成**（程序生成 + 程序 oracle） | 模板 + 随机参数，oracle 由生成器直接给出 | 无限量、天然可验证、**天然防污染**（每次重新生成） | 人造感强；与真实任务的相关性需要单独论证 | 10–20%，主要做压力与回归 |

我在 Reflection 做 math/STEM 数据合成时走的正是"半合成"这条路：从开源数据集和原始文本（教材、论坛、Stack Exchange、竞赛题）出发，用多阶段 LLM 流水线做 question rewriting、answer rewriting 和 QA 转换。那套 pipeline 的质量特征也几乎可以原样搬到 benchmark 任务的验收上：**题目是否自包含、是否含矛盾信息、是否给足了解题所需假设**。这三条在 agent 任务上分别对应：初始状态是否完整、环境里有没有互相矛盾的记录、任务描述有没有漏掉 agent 无法从环境推断的前提。**坏题（题目不可解，或判分本身就是错的）是 benchmark 里最贵的噪声**——OSWorld 原版那 10% 坏在评分脚本，SWE-bench 从 2294 里筛掉的那 1794 题坏在 issue 描述不足、测试过于 specific 和环境失效，两类都属于这个问题。

### 6.2 可验证性是硬约束，而不是加分项 ⭐⭐⭐

**一个任务能进 benchmark 的前提，是它有一个不依赖人的判分方式。** 这条约束会**系统性地重塑任务分布**——它会排除掉开放式、主观、多解的任务，而这些恰好是真实工作的一大部分。

| 级别 | 判分方式 | 例子 | 噪声 | 成本 |
|---|---|---|---|---|
| **L0** 程序化终态 | DB / 文件系统状态比对 | 退款单存在且金额正确 | ~0 | 最低 |
| **L1** 测试通过 | fail-to-pass + pass-to-pass | SWE-bench | 低 | 低，但测试可被泄漏/过拟合 |
| **L2** 唯一短答案 | exact match | GAIA | 低（有假阴性） | 最低，但限死题型 |
| **L3** 约束满足 | 结构化断言集（schema、额度、顺序、数据流） | 政策遵守、过程分 | 低 | 中：每任务要定义 |
| **L4** rubric judge | LLM 按 checklist 逐条判 | 报告质量、解释充分性 | **高** | 中，但必须先校准 |
| **L5** 人工评审 | 专家打分 | 开放式设计任务 | 中 | 最高，只做校准锚 |

**原则：能往上一级走就往上走。** 我在 Reflection 做的"QA 转换"就是这件事的具体形态——把不可验证的题（证明题、开放问答）改写成可验证形式（要求给出最终数值、闭式表达式、或可自动核对的中间量），从而从 L4/L5 降到 L0/L2。

但这个转换**不是无损的**，面试里必须主动说这句：改写会丢掉一部分能力维度（证明的严谨性、解释的可读性）。**所以正确做法是留一个小规模 L4/L5 子集（50–100 题）做对齐**，定期检查"L0 主集的排名"和"L5 子集的排名"是否一致。一旦两者开始背离，说明主集已经被优化到只测那部分可验证的能力了。

> **高分句**：可验证性约束会让 benchmark 系统性地低估"开放式任务"这一整块，从而让人误以为 agent 已经很强。这个覆盖缺口要写进报告的第一页，而不是藏在附录。

### 6.3 难度分层：从 RL 数据筛选借来的方法，以及它的一个关键差异

我在 Reflection 做 RL 数据筛选的做法是：**正式 rollout 前先用 16 条小批量探测每道题的可解率，全对（$p=1$）或全错（$p=0$）的样本直接丢弃——它们提供不了梯度信号——保留下来的样本再跑 128 条。这个筛选阶段大约占 12% 算力。** 思想上和 DAPO 的 dynamic sampling 一致。

**同样的两阶段探测可以直接搬到 benchmark 建设上，但有一个必须点破的差异：**

| | RL 数据 | benchmark |
|---|---|---|
| $p=0$ 的题 | **丢掉**（没梯度） | **不能丢**。它们是天花板信号，也是明年的区分度来源 → 移进 `frontier` 分层单独报 |
| $p=1$ 的题 | **丢掉** | **留一小部分**当 sanity 层。如果模型连这些都挂了，说明 harness 坏了而不是模型退步 |
| 目标 | 最大化梯度信号 | 最大化**区分度**（$p \approx 0.5$ 时二项方差最大） |

由此得到分层结构：

| 层 | 目标 $p$ | 作用 | 占比 | $k$ |
|---|---|---|---|---|
| smoke / sanity | ~1.0 | 检测 harness 有没有坏 | 5% | 1 |
| **core** | 0.3–0.7 | 主区分度来源 | 60% | 5–8 |
| frontier | 0.0–0.15 | 头部空间，明年的主集 | 25% | 1–2 |
| adversarial / safety | n/a（报 violation rate 与 ASR） | 约束遵守、注入、越权 | 10% | 大（估低概率事件） |

必须额外有的一类任务：**不可能任务 / 应当拒绝的任务**——目标在环境里根本无法达成，或者达成它需要越权。正确行为是报告"做不到"而不是编一个结果。绝大多数 benchmark 缺这一层，而它是幻觉与越权行为唯一的直接测量口。

## 7. pass^k 与稳定性 ⭐⭐⭐

### 7.1 公式与直觉

单次成功率 $p$，独立采样 $k$ 次：

- $\mathrm{pass}@k = 1-(1-p)^k$：**任一次**成功即算过 → 测能力上限，**只有在存在廉价 verifier 可以 rerank 时才有决策意义**
- $\mathrm{pass}^k = p^k$：**$k$ 次全成功**才算过 → 测可部署一致性

锚点：$p=0.7$ 时 $\mathrm{pass}@8 \approx 99.99\%$，$\mathrm{pass}^8 \approx 5.7\%$。τ-bench 用 pass^k 就是要暴露这个 gap——客服场景没有"重试到对为止"。

### 7.2 比公式重要得多的一件事：报分布，不报均值 ⭐⭐⭐

**pass^k 的真正信息在 per-task $p$ 的分布，不在平均 $p$。** 两个平均 $p=0.7$ 的系统：

| 系统 | per-task $p$ 分布 | pass@1 | $\mathrm{pass}^8$ | 可部署性 |
|---|---|---|---|---|
| A | 70% 的题 $p=1.0$，30% 的题 $p=0$ | 0.70 | **0.70** | 能上线：失败可预测，把那 30% 路由给人 |
| B | 每题都 $p=0.7$ | 0.70 | **0.057** | 不能上线：任何任务都可能随机挂 |

pass@1 完全一样，可部署性天差地别。所以报告里要有：

```text
stable_pass   (p ≥ 0.9)   ← 可以自动化
flaky         (0.1 < p < 0.9) ← 真正的问题所在
stable_fail   (p ≤ 0.1)   ← 能力缺口，可路由给人
```

> **高分句**：**flaky rate 才是"可部署性"的直接指标**，pass^k 只是它的一个标量摘要。我会把 per-task $p$ 的直方图放在报告第一页，因为改进 flaky 任务（收紧工具 schema、减少对话分支、加重试与幂等）和改进 stable_fail 任务（提升模型能力）是两条完全不同的工程路径。

### 7.3 方差归因：报 pass^k 之前必须先做的事

| 方差源 | 怎么隔离 | 归属 | 该怎么办 |
|---|---|---|---|
| 模型采样（temperature） | 固定 env seed，只变模型 seed | 模型 | 这是要测的东西 |
| 环境随机（初始状态、注入故障） | 固定模型 seed，只变 env seed | benchmark 的**有意**设计 | 保留，但要在报告里分开呈现 |
| user simulator | 固定剧本 vs 自由生成两种模式对比 | benchmark **缺陷** | 压到尽可能小（§5.4） |
| 外部服务 / 时序 | 全部 mock + 录制回放 | benchmark **缺陷** | 必须压到 0 |
| verifier 不确定（LLM judge） | judge 多次投票看一致率 | benchmark **缺陷** | 换成程序化判分，或投票 + 报 judge 一致率 |

做法就是一个嵌套设计的方差分解：固定 A 变 B、固定 B 变 A，各跑几十个任务。

> **高分句**：报一个 pass^k 数字之前，我要先证明这个方差是模型的方差，而不是我 harness 的方差。这两者混在一起时，一个"更稳定的模型"和"一个我修好了的 simulator"在数据上长得一模一样。

### 7.4 $k$ 怎么选，预算怎么分

- **$k$ 由产品的重试预算决定**：有廉价 verifier 且可重试（coding agent 有测试）→ pass@k 有意义；一次性且有副作用（退款、发邮件、改配置）→ 只看 pass^k，$k$ 取"一个用户一天会遇到多少次这类任务"的量级（通常 3–10）。
- **固定总预算下，多题少跑还是少题多跑？** 取决于估什么：
  - 估**平均能力** → 多题少跑（题间方差通常远大于题内方差）
  - 估**一致性 / flaky rate** → 必须题内多跑，$k \geq 5$，否则 per-task $p$ 的估计本身噪声太大（$k=3$ 时 $\hat p$ 只有 4 个取值）
- **实务分配**：core 层 $k=5\text{–}8$、frontier 层 $k=1\text{–}2$、safety 层 $k$ 大（要估的是低概率事件，$k=20$ 才能把 5% 的违规率估到有用的精度）。

## 8. 污染：agent benchmark 一样会被预训练吃掉

### 8.1 三种形态（第二种最难处理）

| 形态 | 具体 | 能否靠改写题目消除 |
|---|---|---|
| **任务/答案记忆** | 题干和 gold patch 就在训练集里（SWE-bench 的仓库、GAIA 验证集的题与答案都公开可下载——而大家报的 GAIA 分数多半就是验证集） | 部分可以 |
| **环境记忆** | 模型见过这个 repo / 这个网站的结构，不需要探索就知道文件在哪、表在哪 | **不能**。这是 agent benchmark 特有的、最难缓解的一类 |
| **运行时泄漏** | agent 在环境里当场搜到答案：联网、`.git`、测试文件、注释里的 TODO | 能，靠环境卫生（§5.3）——这是工程问题不是数据问题 |

### 8.2 检测手段

| 手段 | 做法 | 能查出什么 | 局限 |
|---|---|---|---|
| **时间切分** | 只用模型 cutoff 之后创建的任务 | 记忆型污染（最有力） | 需要持续的新任务来源 |
| **public / private 配对集** | 同分布造两份，一份从不公开 | 总体虚高幅度（一个数字就能说服人） | 造两份的成本 |
| **扰动敏感性** | 改变量名、数值、实体名，看分数掉多少 | 表层记忆 | 掉分也可能是任务变难了，要有对照 |
| **canary 串** | 公开集里埋唯一字符串，之后 probe 模型 | 证明被训过 | 只能证明有，不能量化影响 |
| **前缀补全** | 给题干让模型续写 gold 解 | 强记忆 | 只对 L1/L2 类任务有效 |

### 8.3 设计层面的防御（比事后检测重要）

1. **程序生成 + 参数随机化**：每次评测重新生成实例——这是全合成层最大的价值，也是唯一能长期免疫的路线。
2. **公开 dev / 私有 test**：dev 集给大家迭代，test 集只在发布时跑，**且只返回聚合分不返回逐题结果**（防止通过反复提交反推题目）。
3. **时间滚动**：每季度用新时间窗的任务替换 30%，并保留一小段重叠期用于新旧集的分数校准（否则换题后的分数不可比）。
4. **许可壁垒**：SWE-bench Pro 只用 copyleft 仓库让它在法律上更难进训练集——聪明，但只是延缓。

**诚实边界（要主动说）**：不能承诺零污染。能承诺的是给出**污染上界的估计**和**一个不受污染的对照集**。这个立场和 [07 §8.3](07_pretraining_data.md) 一致。

## 9. 版本漂移：benchmark 是会腐烂的软件产物

| 漂移源 | 表现 | 缓解 |
|---|---|---|
| 依赖升级 | 装不上了；测试因为库行为变化而挂 | 镜像 digest + 完全离线 + 定期 re-baseline（用同一个旧 checkpoint 重跑，分数应当不变） |
| 外部服务 | API 改 schema、限流、下线 | 全部录制回放；真实调用只保留在小的保真度校准集 |
| 站点 / UI 变化 | 选择器失效 | 自托管冻结（WebArena 路线），代价是与现代 web 脱节 |
| 模型接口 | 新模型不支持旧的 function-calling 格式；推理模型多出 thinking 字段 | harness 层抽象；接新模型先跑 sanity 层 |
| **时间语义** | "查最近 7 天的订单"随日历静默改变答案 | 冻结时钟 + 相对时间表述（§5.2） |
| 分数饱和 | 都 95% 了，没有区分度 | 滚动换题、frontier 层扩容 |

两条必须落地的机制：

- **`infra_failure` 必须单独计**，不能算成 agent failure。容器 OOM、429 限流、超时——如果混在一起，你会得出"模型在长任务上更差"的错误结论，而真相是长任务更容易撞超时。报告里要有一行"本次运行 N 题因 infra 原因排除"。
- **re-baseline 制度**：每次改 harness / 升依赖，用一个冻结的旧 checkpoint 重跑全集。分数变化超过噪声带宽就说明这次改动本身移动了标尺，所有历史数字要标注版本。

> **高分句**：这些公开 benchmark 的修订史——SWE-bench→Verified、OSWorld→Verified、τ²→Verified——本身就是最好的设计文档。每一次修订都在补一个我现在可以提前避开的洞：坏题、坏 verifier、policy 不自洽。

## 10. 成本：agent 评测的钱是怎么烧掉的

### 10.1 量级估算（面试要能当场算）

```text
总成本 ≈ N_task × k × E[steps] × tokens/step × price
       + N_task × k × (env 启动 + reset) × 机时
```

代入一组典型值：$N=500$、$k=8$、平均 30 步、每步 8k input（含累积上下文）+ 500 output。

- 单次 rollout ≈ 30 × 8k = **240k input tokens**（未计 prefix cache）
- 总计 4000 次 rollout ≈ **10 亿 input tokens**

结论：**这不是可以每次 commit 都跑的东西。** 采样策略必须是设计的一部分，而不是事后优化。

### 10.2 采样与早停策略

| 策略 | 做法 | 省多少 | 风险 |
|---|---|---|---|
| **分层 CI** | commit 级跑 smoke(5%) + core 的 10% 固定子样；nightly 跑全 core；release 跑全集含 frontier | 10–50× | 子样本必须**分层抽样且固定**，否则不同 commit 之间不可比 |
| **自适应 $k$** | 先每题跑 2–3 次，只对 $\hat p \in [0.2, 0.8]$ 的题追加 rollout | 2–3× | 需要两阶段调度 |
| **序贯早停** | 每题跑到能判定 stable_pass / stable_fail 就停 | 30–50% 的 $k$ | 会**低估 flaky**；早停后报出的 $\hat p$ 有偏 → 只用在 CI 快筛，正式报告用固定 $k$ |
| **不可恢复态剪枝** | 检测到死循环、关键文件已删、预算耗尽即终止 | 20–40% steps | 剪枝规则会误杀"能救回来"的情况，要抽样人工验 |
| **prefix cache** | 系统提示 + 工具 schema 是固定长前缀 | 输入成本 30–70% | 无（应当默认开） |
| **便宜的先跑** | 小模型/短预算先筛掉明显不可解的题 | — | 引入选择偏差，只用于建题阶段不用于评分阶段 |

"自适应 $k$"就是我在 Reflection 做的 **16 条探测 → 128 条正式**这套两阶段调度的直接对应物，可以明说这个迁移。

### 10.3 基础设施：agent eval 的负载形态和 RL rollout 几乎一样

大量并行、任务长尾（有的 5 步结束、有的跑满 100 步）、可被更高优先级作业抢占。我在 Reflection 为 RL 数据生成自建过一套批量推理框架来对付这个问题，直接可复用：

- **pause / resume**：作业能在被抢占时保存进度并在资源回来时续跑，而不是从头再来。对 agent eval 尤其重要——一次 rollout 可能已经烧了 20 分钟。
- **动态申领 / 让出资源**：共享 GPU 池里被其他团队抢占是常态，与其等独占配额不如做成弹性。
- **TCP 式自适应并发调节**：成功就加并发，失败窗口内就退。对付的是外部推理服务的限流和尾延迟。

**诚实边界**：这是离线批量作业的调度，不是在线 serving 的容量规划——我没有大规模在线服务的 oncall 经验，这点要说清楚。

## 11. 常见失败模式：这台仪器最容易在哪坏掉

按"我见过/有公开先例"的具体程度排：

| # | 失败模式 | 具体表现 | 怎么防 |
|---|---|---|---|
| 1 | **任务过于人造** | 初始状态是作者手写的，不是从真实系统 dump 的。agent 在 benchmark 上 80%，接真实数据掉到 30%——因为真实状态有脏数据、重名实体、历史遗留字段 | 留 10–20 题真实 dump 的保真度对照组，定期比对两者的分差 |
| 2 | **verifier 可被 game** | exact match → 输出所有可能答案；测试通过 → 改测试文件；judge → 写长而自信的总结 | verifier 在只读快照上运行；judge 不做主 gate；给 verifier 配 known-bad 轨迹 |
| 3 | **只报总分不分层** | 总分 72% 掩盖"写操作类只有 30%" | 强制分层：任务类型 × 步数分桶 × 是否写操作 × 是否需要多轮澄清 × 领域 |
| 4 | **把 harness 增益报成模型增益** | 同模型换 scaffold 在 Terminal-Bench 上差 15–20pt | harness 当自变量做 ablation；报告里写死 scaffold 版本 |
| 5 | **infra 失败被算成能力失败** | OOM / 429 / 超时混进 failure，得出"长任务更差"的伪结论 | `infra_failure` 独立类别 + 单独报数 |
| 6 | **step budget 没当自变量** | 15 步预算和 50 步预算下是两个不同系统 | 报 success-vs-budget 曲线，至少报两个 budget 点 |
| 7 | **dev 集被人肉过拟合** | 人在 dev 上调 prompt 调了 200 次，等于手动梯度下降 | 从不看逐题结果的 held-out；限制 test 集提交频率 |
| 8 | **judge 与被测模型同源** | 同 family 的 judge 偏好同 family 的输出 | judge 换 family；做一次换 judge 的排名稳定性检验 |
| 9 | **只测能力不测约束** | 全是"能不能完成"，没有"该拒绝时会不会拒绝" | 必须有不可能任务 / 越权任务 / 注入任务层（§6.3） |
| 10 | **单次运行的排名当结论** | 前三名差 1–2pt 就写进结论 | §2.2 的样本量算术；配对检验 + bootstrap CI |
| 11 | **LRM-as-judge 的横向不一致** | 同一条 rubric 在不同题目上判得不一致（我在 Reflection 实际遇到的） | 固定 judge 版本 + 按题型分组校准 + 报 judge 与人工的逐类一致率，而不是一个总的 agreement |

第 11 条值得展开一句：**judge 的问题往往不是"整体准确率低"，而是"在不同子群上的严格程度不一样"**——这会让分层报告里的跨层比较失效。我在 Reflection 做 LRM-as-judge 时遇到的正是这个形态，处理方式是把校准做成分组的而不是全局的。

## 12. 现有 benchmark 的设计取舍：我从每个借一条

主表（分数、失败模式、引用姿势）见 [agentic2 · 04_benchmarks](../agentic_prep/agentic2/04_benchmarks.md)，这里只讲**自建时借什么设计决策**。

| Benchmark | 关键设计选择 | 换来了 | 牺牲了 | 我借这一条 |
|---|---|---|---|---|
| **SWE-bench Verified** | 用真实 issue + 仓库已有单元测试当 verifier；人工从 2294 筛到 500 | 零标注成本的客观 verifier | 只验测试不验代码质量；仓库全在预训练集里 | **fail-to-pass + pass-to-pass 的双向结构**——既验修复也验不回归。这是"过程约束"最廉价的一种形态 |
| **SWE-bench Pro** | copyleft 公共集 + held-out 商业集 | 法律层面的防污染 | grader 仍有 ~1/3 试次误判 | **private held-out 集**这个结构本身 |
| **τ-bench** | LLM 模拟用户 + DB 终态比对 + pass^k | 可自动化的多轮评测；暴露方差 | simulator 是噪声源且可被诱导 | pass^k 的报法 + 终态比对；但我会给 simulator 固定剧本和 seed（§5.4） |
| **τ²-bench** | dual-control：用户侧也持有工具，agent 要指导人操作 | 测协作而非代管 | 更难复现 | "**agent 指导人执行**"这一整类任务——真实客服/IT 支持里这类占比很高 |
| **WebArena** | 自托管冻结站点 | 完全可复现、零真实副作用 | 与现代 web 脱节；evaluator 有假阴性；被 URL 捷径 exploit 过 | 自托管这个决定；但要**为已知捷径写显式的过程断言**（检测到直构 URL 即判 violation） |
| **OSWorld** | 每任务定制 execution-based 评分脚本 | 精确 | 脚本自己会坏（原版 ~10% 任务坏的） | **verifier 要有自己的测试**（§5.5）——这是我最看重的一条教训 |
| **Terminal-Bench 2.0** | harness 公开 + 轨迹公开可查 | 可审计 | 任务分布偏 infra 不偏产品代码 | 把 harness 当自变量做 ablation；**全量轨迹存档**（没有轨迹就没法做失败分类） |
| **GAIA** | exact match 短答案 | 判分零成本 | 限死题型；已饱和 | 短答案层作为**便宜的 smoke 层**，不作主集 |
| **AgentDojo** | utility + ASR 双指标 | 防"砍功能换安全"的假防御 | 静态攻击集过时快 | 双指标同 dashboard + 预留 **adaptive 红队接口**（静态注入集只是回归测试） |

> **高分句**：我引用这些 benchmark 不是为了借分数，是为了借失败模式。它们的修订史就是一部"eval 怎么坏掉"的教科书，而我造的第一版可以直接跳过它们踩过的三个坑：坏题、坏 verifier、被环境泄漏。

## 13. 10 分钟口述稿

> 我先把这道题定位一下：这是一道**测量系统设计题**。交付物不是一个更强的 agent，而是一台能稳定分辨两个 agent 谁更强、并且能说清自己误差有多大的仪器。所以我会先定这台仪器自己的成功标准，再谈任务和环境。
>
> **澄清三件事**：这个 benchmark 服务谁的决策（上线 gate 要能分辨 2–3 个点，选型只要分辨 10 个点，噪声预算差一个数量级）；被测的是模型还是"模型 + scaffold"这整套系统（同一模型换 harness 在 Terminal-Bench 上差 15–20 个点，不锁死这层所有对比都不成立）；以及 agent 有没有写权限——有写操作就必须全程快照回滚，而且要专门测"该拒绝时会不会拒绝"。
>
> **元指标**。我要报的第一个数不是准确率，是**噪声下界**：同一个 checkpoint 跑两遍分差多少。因为 500 题、每题跑一次的 benchmark，未配对时只能可靠分辨 9 个点左右的差异——榜单上前三名彼此在噪声之内是常态。所以我的报告主指标永远带 bootstrap 置信区间，模型对比永远用配对检验而不是排名。除了噪声，还要报区分度、与线上的秩相关、抗污染幅度、单次评测成本、以及失败是否可诊断。
>
> **为什么 agent 评测比单轮难**，我总结成四条结构差异：多步导致误差累积和信用分配问题——单步 0.98、50 步只剩 0.36，所以终态成功率把"每步都对"和"错了能救回来"压成了同一个数字；有状态导致步与步之间不独立，不能当独立样本做统计；有副作用导致沙箱和回滚是基础设施；路径不唯一导致过程评分必须写成约束满足而不是脚本匹配。
>
> **核心是过程 vs 结果**。只看终态会漏掉四类：蒙对的、绕过约束达成目标的、代价不可见的、以及过程全对但被外部 5xx 打断的假阴性。第二类最危险——**它在终态上和正确行为完全不可区分**。我在自己搭的一个退款流程实验里量化过这件事：153 条轨迹、五步合规流程，只看结果时"合规"和"跳步""乱序""超额"四类**全是满分，完全平局**；而一旦加上任何效率项——每次工具调用扣 0.05，任何真实系统都会关心延迟和成本——**跳步的分数就严格高于合规**，0.80 对 0.75。跳过校验少调一次工具、同样拿到退款，净赚。所以过程约束必须是一个独立的否决维度，不能做成总分里的加权项。
>
> 过程分怎么落地：我按可靠性排四种——必经点断言、中间状态比对、**反事实探针**、以及 LLM judge 读 trace，最后一种不做主判分。反事实探针是最值钱的，因为它绕开了"路径不唯一"这个根本困难：不检查 agent 走了哪条路，只造一对除了"订单是否在退款窗口内"之外完全相同的任务，看它的行为是否随前提改变。真的做了校验的 agent 一个退一个拒，跳步的 agent 两个都退——**成对任务的行为差分才是能力证据**。这和我在一次 take-home 里做的 137 对扰动测试套件是同一个方法，而且当时是按扰动类型分层报检出率的，因为总检出率会掩盖"对某一类完全无感"这种致命缺口。
>
> **环境**上我要三档而不是两档：全确定的做回归 CI，**受控随机**的做主集——注入确定性故障来测恢复能力，真实随机只留 20–50 题做保真度校准。原则是方差要么消除、要么可归因，不能既存在又不可控，所以所有 seed、镜像 digest、simulator 版本、故障 schedule 都写进 run manifest，任何失败都能精确重放。可复现要锁四层：依赖、状态快照、**时钟**、随机种子——时钟这层最容易漏，"查最近 7 天订单"这种任务的答案会随日历静默改变。还有一条我一定会说：**verifier 是 benchmark 里唯一没人评测的组件**。OSWorld 原版 10% 的任务是坏的、SWE-bench Pro 的 grader 被审计出三分之一试次误判，根因都是这个。所以每个任务要配一条 gold 轨迹和一条已知坏轨迹当单元测试，每天在 CI 里跑。
>
> **任务来源**：真实采集为主 50–70%，半合成 20–40% 用来造反事实对，全合成 10–20% 做压力和防污染。硬约束是**可验证性**——我会按 L0 程序化终态 / L1 测试 / L2 短答案 / L3 约束断言 / L4 rubric / L5 人工排一个阶梯，能往上走就往上走。我在现在的工作里做过一件直接对口的事：把不可验证的题改写成可验证形式，让它从 L4 降到 L0。但这个转换不是无损的，会丢掉证明严谨性这类维度，所以要留一个 50–100 题的 L5 子集做对齐，一旦主集和子集的排名开始背离，说明主集已经被优化到只测那部分可验证的能力了。**这个覆盖缺口要写在报告第一页而不是附录。**
>
> **难度分层**我借用自己做 RL 数据筛选的方法：先用 16 条小批量探测每题的可解率再决定要不要正式跑，筛选大概占 12% 算力。但 benchmark 和 RL 数据有一个关键差异——RL 里全对全错的题该丢，因为没梯度；benchmark 里全错的题不能丢，它们是明年的区分度来源，要移到 frontier 分层单独报；全对的题也要留一小部分当 sanity 层，模型连这些都挂说明是 harness 坏了。
>
> **稳定性**我报 pass^k，但更重要的是**报 per-task p 的分布而不是均值**。两个平均成功率都 70% 的系统：一个是 70% 的题稳定成功、30% 稳定失败，pass^8 还有 0.70，可以上线并把失败的那部分路由给人；另一个是每题都 70% 概率成功，pass^8 只剩 5.7%，不能上线。pass@1 完全一样。所以我会把任务分成 stable_pass / flaky / stable_fail 三类，**flaky rate 才是可部署性的直接指标**。而且在报 pass^k 之前我要先做方差归因——模型采样的方差是要测的，simulator 和外部服务的方差是我 harness 的缺陷，混在一起时"更稳定的模型"和"我修好了 simulator"在数据上长得一样。
>
> **污染**上 agent benchmark 有一类特殊形态：环境记忆——模型见过这个 repo、这个网站，不用探索就知道结构在哪，**这个改写题目消不掉**。防御靠程序生成 + 参数随机化、公开 dev / 私有 test 且只返回聚合分、按季度滚动换 30% 题、以及时间切分。我不会承诺零污染，只承诺给出污染上界的估计和一个不受污染的对照集。
>
> **成本**：500 题 × k=8 × 30 步，一次完整评测就是十亿量级的 input token，这不是每次 commit 能跑的东西。所以分层 CI——commit 跑 smoke 加 core 的固定 10% 子样，nightly 跑全 core，release 跑全集；再加自适应 k，只对 p 落在 0.2 到 0.8 的题追加 rollout，这正是我在工作里那套两阶段探测调度的迁移。序贯早停能再省三到五成，但它会低估 flaky，所以只用在 CI 快筛，正式报告用固定 k。
>
> **最容易坏的三个地方**：任务人造导致离线到线上外推失败、verifier 被 game 或者自己坏掉、以及 infra 失败被算成能力失败——最后这个会直接得出"模型在长任务上更差"的伪结论，真相是长任务更容易撞超时。

## 14. 面试前一页速记

**定位**：测量系统设计题。交付物是一台仪器，不是一个 agent。**先测噪声，再定题量。**

**元指标七件**：区分度 / test-retest 噪声 / 可复现 / 与线上秩相关 / 抗污染 / 成本 / 可诊断。

**样本量算术**：未配对 $\mathrm{SE}=\sqrt{2p(1-p)/n}$，$p{=}0.5$、$n{=}500$ → SE 3.2pt → 只能分辨 ~9pt；配对（不一致率 0.2）→ ~5pt。**榜单前三名在噪声内是常态。**

**四条结构差异**：多步（误差累积，0.98^50=0.36）/ 有状态（reset 速度决定 $k$）/ 有副作用（沙箱+回滚）/ 路径不唯一（约束满足 ≠ 脚本匹配）。

**过程 vs 结果的实证**：153 条退款轨迹，final_only 下合规与三类违规**全是 1.000 平局**；加效率项后 skip_step **0.800 > compliant 0.750**。→ 过程是**否决维度**不是加权项。三分类判分：success / incomplete / violation。

**过程评分四法**（可靠性降序）：必经点断言 → 中间状态比对 → **反事实探针**（治"蒙对"，成对任务的行为差分）→ judge 读 trace（不做主 gate）。断言绑**数据流**（refund 的 order_id 必须来自 lookup 的返回），否则 agent 会"调了但不看返回值"。

**环境三档**：全确定（回归 CI）/ **受控随机 + 注入故障**（主集，测 recovery）/ 真实随机（20–50 题保真度校准）。可复现锁四层：依赖 digest / 状态快照 / **时钟** / seed。

**verifier 要被测试**：每题配 gold 轨迹 + known-bad 轨迹，CI 每日跑。先例：OSWorld 原版 ~10% 坏题，SWE-bench Pro grader ~1/3 试次误判。

**环境卫生**：strip `.git`、测试文件延后挂载、网络 deny、verifier 只读、真实副作用硬失败不静默 mock。

**任务来源**：真实 50–70% / 半合成 20–40%（造反事实对）/ 全合成 10–20%（防污染）。**可验证性阶梯 L0 终态 → L1 测试 → L2 短答案 → L3 约束 → L4 rubric → L5 人工**，能往上走就往上走；但留 50–100 题 L5 子集做对齐，覆盖缺口写第一页。

**分层**：smoke 5%（$p{\approx}1$，测 harness）/ core 60%（$p$ 0.3–0.7，$k$=5–8）/ frontier 25%（$p$<0.15）/ adversarial 10%。**RL 里丢 $p{=}0$ 的题，benchmark 里不能丢**——移到 frontier。必须有**不可能任务 / 该拒绝的任务**。

**pass^k**：$p{=}0.7 \Rightarrow \mathrm{pass}@8{=}99.99\%$，$\mathrm{pass}^8{=}5.7\%$。**报 per-task $p$ 的分布不报均值**：0.7/0.3 双峰 → pass^8=0.70 能上线；全 0.7 → pass^8=0.057 不能。**flaky rate 才是可部署性指标。** 报之前先做方差归因。

**污染三形态**：任务记忆（可改写）/ **环境记忆（改不掉）** / 运行时泄漏（环境卫生）。防御：程序生成 + 私有 test 只返聚合分 + 季度滚动 30% + 时间切分。不承诺零污染。

**成本**：500×8×30 步 ≈ 10 亿 input token。分层 CI + 自适应 $k$（只对 $p\in[0.2,0.8]$ 追加）+ prefix cache。序贯早停会低估 flaky，只用于快筛。

**必背句**：
- 只看结果的评测在现实中不存在——总会叠效率项，而那个组合会把最高分发给绕过合规的 agent。
- 过程分不是给成功的 agent 加分，是给"看起来成功"的 agent 减分。
- 报 pass^k 之前先证明这个方差是模型的方差，不是我 harness 的方差。
- verifier 是 benchmark 里唯一没人评测的组件。
- 我引用公开 benchmark 是为了借它的失败模式，不是借它的分数。

## 15. 常见追问 + 应答要点

1. **"为什么不能只看最终成功率？就业务而言不就是看结果吗？"**
   业务确实只看结果，但 benchmark 是**预测器**不是记录仪。终态指标对"绕过约束达成目标"完全失明——退款跳过身份验证和正确退款在数据库里长得一样。而且现实中没有纯结果指标，只要叠一个效率项，违规就严格胜出（举 0.800 vs 0.750 那组数）。业务看结果，benchmark 必须多看一层，否则它预测不了下一次会不会出事故。

2. **"过程分会不会惩罚比人聪明的解法？"**
   会——如果写成脚本匹配。所以断言写成**约束**（`verify_identity` 必须在 `issue_refund` 之前完成）而不是**顺序脚本**（第一步必须是 X）。允许 agent 用一次批量查询代替三次单查。判断标准：这条断言删掉之后，是否存在一条既安全又更优的路径被误判——有的话说明断言写得太紧。

3. **"多少题够？"**
   反问要检测多大效应量。$p\approx0.5$、未配对、每题跑一次时 SE $=\sqrt{2p(1-p)/n}$；要分辨 5pt 需要 $n\approx1500$，配对设计能降到 500 上下。再叠 run-to-run 方差还要恶化。**所以我先测 test-retest 噪声，再反推题量**，不先拍一个数字。

4. **"pass^k 的 $k$ 怎么选？"**
   由产品的重试预算决定。有廉价 verifier 且可重试 → pass@k；一次性有副作用 → pass^k，$k$ 取用户一天遇到这类任务的次数量级（3–10）。另外 $k$ 还要够大到能估 per-task $p$——$k=3$ 时 $\hat p$ 只有 4 个取值，算不出有意义的 flaky rate。

5. **"user simulator 用什么模型？会不会有同源偏差？"**
   会。同 family 的 simulator 和 agent 会共享同样的误解并互相配合。做法：simulator 用不同 family、固定版本与 seed、给剧本约束（persona + 已知信息 + **不能主动透露的信息**）、**绝不持有判分权**。并且做一次换 simulator 模型的排名稳定性检验——排名翻了说明测的是 simulator 不是 agent。

6. **"怎么防止 agent 在环境里作弊？"**
   分两层。**环境卫生**：strip `.git`、测试文件延后挂载、网络 deny、verifier 代码只读、答案不出现在任何 fixture 里。**行为检测**：为已知捷径写显式断言（直构 URL、改测试文件、读评分脚本一律判 violation），并且抽样人工读轨迹——**新的作弊方式只能靠读轨迹发现**。我在工作里手动检查 trace 时抓到过格式化推理、失控推理、错误推理、reward hacking 四类异常，这类东西聚合指标上是看不见的。

7. **"任务本身没有可程序化终态怎么办（写报告、做设计）？"**
   三步降级：先看能不能把任务改写成可验证形式（要求输出结构化结论、可核对的数值、明确的引用）——我做过这种 QA 转换；改不动的用 L3 约束断言拆成多个可判定的子条件（是否引用了这三份材料、是否覆盖了这四个必答点）；仍然不行的才上 rubric judge，且必须先用人工标注算 AUROC 和分层检出率来证明这个 judge 有用——我做过一次这样的验证，被验的自动指标 AUROC 只有 0.569，等于掷硬币。

8. **"离线 benchmark 的分数能外推到线上吗？"**
   默认不能，必须实测相关性：拿已上线的若干版本，算离线分与线上指标的秩相关。相关性低时优先怀疑任务分布（初始状态是手写的还是从真实系统 dump 的）。**诚实边界**：大规模在线实验的指标设计、延迟指标 join 和 cohort 分析我在 Meta 做推荐时做过，这套方法论我是熟的；但 LLM/agent 产品的线上 serving 和 oncall 我没做过，所以这一段我给的是设计，会找有线上经验的同事校准口径。

9. **"benchmark 饱和了怎么办？"**
   饱和是设计里就该预留的。frontier 层从第一天就要有（占 25%），并且按季度用新时间窗任务换掉 30%，换题时保留重叠期做新旧校准，否则换题前后的分数不可比。另外饱和常常是假的——把总分拆到写操作、长步数、多轮澄清这些分层上，通常还有大量空间。

10. **"你怎么证明你的 benchmark 比现有的好？"**
    不比"好"，比**互补**和**可用**。给三个数：(a) 与现有 benchmark 的排名相关性（如果完全一致，那我没提供新信息）；(b) test-retest 噪声比现有的小多少；(c) 与线上指标的秩相关比现有的高多少。再加一条定性的：现有 benchmark 测不到的那类失败，我能测到（比如绕过约束达成目标）。

11. **"LLM judge 到底能不能用？"**
    能用，但不能当主 gate，也不能只报一个平均分。用法是：先用人工标注做校准并**分层**报一致率——我遇到过同一条 rubric 在不同题型上判得松紧不一致的情况，全局 agreement 会把这掩盖掉；judge 换 family、固定版本、temperature=0、多次投票并报一致率；分歧样本进人工。更根本的是尽量把任务往可验证阶梯上推，减少对 judge 的依赖。参见 [08 §5](08_evaluation_production.md)。

12. **"我们的模型在你的 benchmark 上涨了 5 个点，你信吗？"**
    先看四件事：这 5 点是否超过 test-retest 噪声带宽；是配对比较还是各跑各的；harness / 依赖 / prompt 模板有没有同时变（变了就是混杂）；涨的是哪几层——如果只涨在 core 层而 frontier 和 adversarial 层没动，可能是对已知题型的适配而不是能力提升。都过了我才信，而且我会要求在私有 held-out 集上复现一次。

13. **"评测预算只有现在的十分之一怎么办？"**
    按序砍：先砍 frontier 层的 $k$（那层反正 $p$ 低，$k=1$ 就够）→ 用固定的分层子样代替全集（子样必须固定且分层，否则跨版本不可比）→ 开 prefix cache 和不可恢复态剪枝 → 最后才砍 core 层的 $k$，因为砍它等于放弃 flaky rate，而那是可部署性的唯一直接指标。**绝不砍的是 sanity 层和 verifier CI**——它们最便宜，且是防止整批结果无效的保险。

14. **"如果我只给你两周，你先做什么？"**
    第一周：50 题的最小可用集（覆盖三个任务类型），全部 L0/L1 判分，配 gold + known-bad 轨迹，把 harness 和 run manifest 打通。第二周：测 test-retest 噪声，用两个已知强弱差异的系统验区分度。**在噪声和区分度这两个数出来之前，我不会用它做任何决策**——一个没测过噪声的 benchmark 比没有 benchmark 更危险，因为它会给出有信心的错误结论。
